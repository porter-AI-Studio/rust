第 4 章 · Part 1：認識 Rust

Rust 與 Go：什麼時候選哪一個

不是誰比較強，而是你的專案在乎速度、確定性，還是開發效率。

這一章的素材有三份：LogRocket 部落格的 Go vs. Rust 比較（頁面註明 2024 年 11 月 19 日更新）、Relia Software 的 2025 年 Rust vs Go 比較，以及 Discord 官方工程部落格的案例。前兩篇是第三方整理，第三篇是公司自述的單一案例，三者的證據強度不同，下文會標明出處。

設計哲學：簡單 vs. 控制

Go 由 Google 的工程師設計，2009 年公開，目標是提供比 C++ 更容易學、更容易寫、且針對多核心 CPU 最佳化的替代品（LogRocket）。Relia 的整理則是：Go 追求簡單與務實，重視生產力與可讀性，適合不同經驗的團隊協作；Rust 出身自 Mozilla Research，目標是在編譯期消除常見的程式錯誤，尤其是記憶體管理相關的，給開發者對系統資源的高度控制。

面向RustGo
設計哲學安全、控制、零成本抽象簡單、速度、易用
記憶體管理所有權模型，沒有 GC自動垃圾回收
效能執行速度較快、可做底層最佳化編譯與迭代速度較快
並行安全的執行緒、async/await、編譯期檢查goroutine 加 channel
學習曲線陡（所有權、生命週期、trait）平緩（語法精簡、概念少）
錯誤處理Result 型別明確表示可能失敗，未處理的結果通常會得到編譯器警告回傳值加明確檢查

上表整理自 Relia 的比較表。兩者都產生獨立執行檔，部署起來都單純；差別在於 Rust 把「誰釋放記憶體」交給編譯期規則，Go 交給執行期的垃圾回收器。

記憶體管理：所有權 vs. GC

Relia 用兩段小程式說明差異：Rust 的 s 被搬進函式後就不能再用，編譯器擋下；Go 的字串則可以隨意傳遞，因為執行期負責配置與清理。以下兩段程式都取自 Relia。

Rust 的所有權搬移（取自 Relia Software 比較文章）
fn main() {
    let s = String::from("hello");
    takes_ownership(s); // s is moved here
    // println!("{}", s); // Error: value borrowed here after move
}

fn takes_ownership(some_string: String) {
    println!("{}", some_string);
}
Go 不需要想所有權（取自 Relia Software 比較文章）
package main

import "fmt"

func main() {
    s := "hello"
    fmt.Println(s) // s can still be used freely
}

Relia 認為所有權消除了 use-after-free、double-free、並行資料競爭與空指標解參考等一整類錯誤，代價是前期更陡的學習曲線。有一點兩份素材說法不同：Relia 提到即使沒有任何 unsafe 程式碼，Rust 程式仍可能有記憶體安全漏洞，只是比沒有這套保證的語言少見；Discord 的文章腳註則寫「除非你使用 unsafe」，否則幾乎不可能有執行期記憶體 bug。兩者並陳，結論是：安全保證很強，但不是絕對。

效能與基準測試

LogRocket 與 Relia 都引用 Benchmarks Game：所有測試演算法中，最佳化後的 Rust 程式碼至少比最佳化後的 Go 快 30%，binary-trees 一項快了 12 倍。LogRocket 還說很多情況下連最沒最佳化的 Rust 都比最佳化的 Go 快。Relia 則補充 Go 的優勢在於編譯速度，常在幾秒內完成，Rust 編譯較慢。需要留意兩點：這兩份文章的基準數字有相同來源，不是兩次獨立量測；而 LogRocket 自己也提醒個別基準測試容易被操弄、不易解讀。實際專案請用自己的工作負載量測。

並行：goroutine 的便利 vs. 編譯期安全

Go 啟動 goroutine 只要在函式前加 go；LogRocket 也指出，就並行的開發體驗而言 Go 有優勢，而 Rust 的優勢是更能保證記憶體安全，且 Rust 原生 async/await 的出現相對較晚。Relia 稱 goroutine 只需數 KB 記憶體，可輕鬆啟動成千上萬個。Rust 這一側，則靠所有權與型別系統在編譯期排除資料競爭，並有系統執行緒、async/await、rayon 平行迭代與訊息傳遞等選項。下面是 Relia 的兩個並行範例。

Go 的 goroutine（取自 Relia Software）
package main

import (
    "fmt"
    "time"
)

func say(msg string) {
    for i := 0; i < 3; i++ {
        fmt.Println(msg)
        time.Sleep(100 * time.Millisecond)
    }
}

func main() {
    go say("Goroutine")
    say("Main")
}
Rust 的執行緒（取自 Relia Software）
use std::thread;

fn main() {
    let handle = thread::spawn(|| {
        for _ in 0..3 {
            println!("From spawned thread");
        }
    });

    for _ in 0..3 {
        println!("From main thread");
    }

    handle.join().unwrap();
}

Go 另有內建的 race detector，用 -race 旗標在建置或測試時啟用，於執行期偵測競爭條件並回報位置（LogRocket）；Rust 則是在編譯期就拒絕有資料競爭風險的程式。兩者防護的時間點不同。Rust 的並行與 async 會在第 12、13 章完整介紹。

學習曲線與開發速度

Relia 指出，Rust 往往需要數週到數個月才能熟悉，Go 多半幾天到幾週就能上手；它引用 Stack Overflow 開發者調查，說 84% 的 Rust 開發者想繼續使用，Go 則為 60%。這是 Relia 轉述的調查結果，素材沒有附原始問卷，請視為參考。LogRocket 補充了開發循環的差異：Go 容易寫、容易協作，但 nil 與錯誤檢查靠開發者自己小心，編譯器幫不上忙；Rust 寫起來和編譯起來較棘手，但編譯器會抓出這些問題並給出清楚訊息，所以「編譯通過就大致正確」雖然兩者都不成立，卻更接近 Rust，改既有程式碼時更有信心。

案例：Discord 把 Read States 從 Go 改寫成 Rust

Discord 的 Read States 服務負責記錄你在每個頻道讀到哪則訊息，每次連線、發訊息與讀訊息都會存取，位於熱路徑上。據文章自述：Discord 有數十億筆 Read State，每個使用者每個頻道一筆；每台伺服器有一個 LRU 快取，內含數千萬筆、每秒數十萬次更新，並以 Cassandra 持久化。Go 版本大多時候很快，但大約每兩分鐘就出現延遲與 CPU 尖峰。

團隊查到原因：Go 會在至少每兩分鐘強制執行一次垃圾回收，而回收器需要掃描整個 LRU 快取，才能確認哪些記憶體真的沒有被引用。調整 GC 百分比沒有效果；縮小快取能降低尖峰，卻拉高第 99 百分位延遲，因為快取命中率下降。改寫為 Rust 之後，快取項目被逐出時記憶體會立刻釋放，不需要等回收器。作者說，只做了基本最佳化的 Rust 版本，延遲與 Go 一樣好且沒有尖峰，再經過少量最佳化後，延遲、CPU 與記憶體每個指標都勝過 Go；之後把快取容量提高到 800 萬筆，平均時間改以微秒計。

Discord 自己在腳註說：不認為你該為了改寫而改寫，只會在適合的地方使用 Rust。這個服務小而獨立、處於熱路徑、延遲尖峰直接影響使用者體驗，才是它適合重寫的原因。圖表中的具體數字，素材只有圖片，本章未引用。
