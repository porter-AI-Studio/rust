第 11 章 · Part 3：型別系統與錯誤處理

智慧指標與 unsafe

需要把資料放上堆積、讓多個擁有者共享一份資料，或做編譯器無法驗證的底層操作時，Rust 提供什麼工具。

前面幾章談的所有權規則，預設是「每個值都有一個擁有者」；至於資料放在堆疊或堆積，則是另一個問題，前面的章節已經看過 String 這類值的內容放在堆積。現實裡常會遇到例外：資料大小在編譯期不確定、需要多個擁有者共享一份資料，或是要和 C 程式、硬體打交道。本章先看兩個最常用的智慧指標 Box<T> 與 Rc<T>，再看 Rust 如何用 unsafe 這個明確標示出來的逃生口處理底層需求。範例取自 Rust 官方文件 The Rust Programming Language（以下簡稱 Rust Book）與 The Rustonomicon。

Box<T>：把資料放到堆積上

Box 是最直接的智慧指標，型別寫成 Box<T>。資料存在堆積上，堆疊上留下的只有指向堆積資料的指標。Rust Book 說明 Box 除了「資料放在堆積而非堆疊」之外，沒有額外的執行期成本，也沒有太多額外功能。常見用途有三種：

  • 型別大小在編譯期無法得知，卻要在需要確定大小的地方使用它（例如遞迴型別）。
  • 有大量資料，想轉移所有權但避免資料被複製。
  • 只關心某個值實作了特定 trait，而不在乎具體型別。

最基本的用法如下，印出 b = 5。官方也說明，單獨把一個 i32 放上堆積並不實用，這類值放在堆疊上更合適：

Rust Book Listing 15-1：Box 的基本用法
fn main() {
    let b = Box::new(5);
    println!("b = {b}");
}

用 Box 讓遞迴型別有確定大小

遞迴型別的值可以包含另一個同型別的值，但 Rust 必須在編譯期知道每個型別佔多少空間。官方用 cons list（源自 Lisp 的巢狀配對資料結構，如 (1, (2, (3, Nil)))）示範。Rust Book 也提醒：cons list 在 Rust 中不常用，大多數時候清單用 Vec<T> 就好。直接定義的版本無法編譯：

Rust Book Listing 15-2／15-3：直接遞迴（無法編譯）
enum List {
    Cons(i32, List),
    Nil,
}

use crate::List::{Cons, Nil};

fn main() {
    let list = Cons(1, Cons(2, Cons(3, Nil)));
}
Rust Book Listing 15-4：編譯器回報型別大小無限
error[E0072]: recursive type `List` has infinite size
 --> src/main.rs:1:1
  |
1 | enum List {
  | ^^^^^^^^^
2 |     Cons(i32, List),
  |               ---- recursive without indirection
  |
help: insert some indirection (e.g., a `Box`, `Rc`, or `&`) to break the cycle
  |
2 |     Cons(i32, Box<List>),
  |               ++++    +

編譯器的建議是插入間接層（indirection），例如 Box。指標的大小不會隨它指向的資料而改變，所以 Box<List> 的大小是固定的，List 的大小也就能算出來：

Rust Book Listing 15-5：用 Box 打斷無限遞迴
enum List {
    Cons(i32, Box<List>),
    Nil,
}

use crate::List::{Cons, Nil};

fn main() {
    let list = Cons(1, Box::new(Cons(2, Box::new(Cons(3, Box::new(Nil))))));
}

Rust Book 說明 Box<T> 之所以是智慧指標，是因為它實作了 Deref trait，所以可以像參考一樣使用；離開作用域時，Box 指向的堆積資料也會一併被釋放。（本章素材未展開 Deref 與 Drop 的細節。）

Rc<T>：多個擁有者共享資料

多數情況下誰擁有某個值是很清楚的，但有些情況一個值確實需要多個擁有者。Rust Book 舉的例子是圖資料結構：多條邊可能指向同一個節點，只有在沒有任何邊指向它時才能清除。要啟用多重所有權，必須明確使用 Rc<T>（reference counting，參考計數）。它記錄參考數量，數量歸零時資料才被清理。官方用客廳的電視比喻：第一個人進來打開電視，最後一個人離開時關掉。

回到 cons list：想讓清單 b 與 c 共用清單 a 作為尾巴，用 Box 行不通，因為第一次建立 b 時 a 就被移動進去了：

Rust Book Listing 15-17 的編譯錯誤（節錄）
error[E0382]: use of moved value: `a`
  --> src/main.rs:11:30
   |
 9 |     let a = Cons(5, Box::new(Cons(10, Box::new(Nil))));
   |         - move occurs because `a` has type `List`, which does not implement the `Copy` trait
10 |     let b = Cons(3, Box::new(a));
   |                              - value moved here
11 |     let c = Cons(4, Box::new(a));
   |                              ^ value used here after move

改用 Rc<T>，並以 Rc::clone(&a) 取得共享參考。Rust Book 說明 Rc::clone 不會像多數型別的 clone 那樣深層複製資料，只是增加參考計數；慣例上這裡寫 Rc::clone(&a) 而不是 a.clone()。下面用 Rc::strong_count 觀察計數變化：

Rust Book Listing 15-19：觀察 Rc 的參考計數
enum List {
    Cons(i32, Rc<List>),
    Nil,
}

use crate::List::{Cons, Nil};
use std::rc::Rc;

fn main() {
    let a = Rc::new(Cons(5, Rc::new(Cons(10, Rc::new(Nil)))));
    println!("count after creating a = {}", Rc::strong_count(&a));
    let b = Cons(3, Rc::clone(&a));
    println!("count after creating b = {}", Rc::strong_count(&a));
    {
        let c = Cons(4, Rc::clone(&a));
        println!("count after creating c = {}", Rc::strong_count(&a));
    }
    println!("count after c goes out of scope = {}", Rc::strong_count(&a));
}
Rust Book：輸出
count after creating a = 1
count after creating b = 2
count after creating c = 3
count after c goes out of scope = 2

計數在建立 b、c 時增加，c 離開作用域時自動減少，不必手動呼叫函式。

⚠️
Rc 的限制

Rust Book 指出：Rc<T> 只能用在單執行緒情境；跨執行緒的參考計數要用其他型別，下一章會談到。此外，Rc<T> 透過不可變參考提供唯讀共享；若允許多個可變參考，會違反借用規則。需要修改共享資料的做法，不在本章素材範圍內。

unsafe Rust：離開編譯器保護的明確邊界

Rust Book 說 Rust 內藏第二種語言：unsafe Rust，它不強制檢查記憶體安全。存在的原因有兩個：靜態分析本質上是保守的，寧可拒絕一些其實合法的程式，也不要放行不合法的程式；而且底層硬體本身就是不安全的，若不允許不安全的操作，就無法做系統程式設計（如直接與作業系統互動，甚至寫作業系統）。

用 unsafe 區塊可以做五件「超能力」操作：

  1. 解參考（dereference）raw pointer。
  2. 呼叫 unsafe 函式或方法。
  3. 存取或修改可變的 static 變數。
  4. 實作 unsafe trait。
  5. 存取 union 的欄位。

重點是：unsafe 並不會關閉借用檢查器或其他安全檢查，它只是讓你可以做上面五件事；也不代表區塊內的程式碼一定危險，而是由你這位程式設計師向編譯器保證它不會出記憶體問題。好處是，與記憶體安全相關的錯誤只可能出現在 unsafe 區塊內，所以要盡量縮小區塊，並用安全的 API 把它包起來。

Raw pointer

raw pointer 有 *const T 與 *mut T 兩種。和參考與智慧指標不同，它可以同時有可變與不可變指標、不保證指向有效記憶體、可以是 null、也不會自動清理。建立 raw pointer 不需要 unsafe，只有解參考才需要：

Rust Book Listing 20-1／20-3：建立並解參考 raw pointer
fn main() {
    let mut num = 5;

    let r1 = &raw const num;
    let r2 = &raw mut num;

    unsafe {
        println!("r1 is: {}", *r1);
        println!("r2 is: {}", *r2);
    }
}

官方指出 raw pointer 的主要用途是與 C 程式介接，或建構借用檢查器無法理解的安全抽象。

unsafe 函式與安全抽象

unsafe 函式在定義前多一個 unsafe，呼叫時必須放進 unsafe 區塊，表示你已讀過它的文件並確認遵守了它的契約。

Rust Book Listing 20-4：unsafe 函式
fn main() {
    unsafe fn dangerous() {}

    unsafe {
        dangerous();
    }
}

函式內含 unsafe 程式碼，並不代表整個函式要標成 unsafe。常見做法是把它包成安全函式。官方以標準函式庫的 split_at_mut 為例：它把一個可變切片分成兩段，但只用安全 Rust 寫會被借用檢查器擋下，因為編譯器看不出兩次借用的是切片中不重疊的部分：

Rust Book Listing 20-5 的編譯錯誤（節錄）
error[E0499]: cannot borrow `*values` as mutable more than once at a time
 --> src/main.rs:6:31
  |
1 | fn split_at_mut(values: &mut [i32], mid: usize) -> (&mut [i32], &mut [i32]) {
  |                         - let's call the lifetime of this reference `'1`
...
6 |     (&mut values[..mid], &mut values[mid..])
  |     --------------------------^^^^^^--------
  |     |     |                   |
  |     |     |                   second mutable borrow occurs here
  |     |     first mutable borrow occurs here
  |     returning this value requires that `*values` is borrowed for `'1`
Rust Book Listing 20-6：以 unsafe 實作，對外仍是安全函式
use std::slice;

fn split_at_mut(values: &mut [i32], mid: usize) -> (&mut [i32], &mut [i32]) {
    let len = values.len();
    let ptr = values.as_mut_ptr();

    assert!(mid <= len);

    unsafe {
        (
            slice::from_raw_parts_mut(ptr, mid),
            slice::from_raw_parts_mut(ptr.add(mid), len - mid),
        )
    }
}

fn main() {
    let mut vector = vec![1, 2, 3, 4, 5, 6];
    let (left, right) = split_at_mut(&mut vector, 3);
}

這裡保留了 assert!(mid <= len)，並只在小範圍內使用 slice::from_raw_parts_mut 與 ptr.add。因為它們必須信任指標有效，所以是 unsafe；但 split_at_mut 本身不必標成 unsafe，可以從安全程式碼呼叫。

extern：呼叫 C 程式碼

透過 extern 建立 FFI（Foreign Function Interface）。"C" 指定外部函式使用的 ABI（application binary interface）。下例呼叫 C 標準函式庫的 abs：

Rust Book Listing 20-8：呼叫 C 的 abs
unsafe extern "C" {
    fn abs(input: i32) -> i32;
}

fn main() {
    unsafe {
        println!("Absolute value of -3 according to C: {}", abs(-3));
    }
}

官方也提到 unsafe extern 區塊內的項目預設為 unsafe，確定安全的可以標 safe fn，但這只是你對 Rust 的承諾，不會讓函式真的變安全。反方向（讓 C 呼叫 Rust 函式）則使用 #[unsafe(no_mangle)] 搭配 pub extern "C" fn。

可變的 static 變數

Rust 的全域變數叫 static。可變的 static 變數若被多個執行緒存取，可能造成資料競爭，所以讀寫都必須放在 unsafe 內。官方範例展示了慣例：unsafe 函式寫一段以 SAFETY 開頭的註解，說明呼叫者要滿足什麼條件。另外編譯器預設會拒絕建立指向可變 static 的參考，所以這裡用 &raw const 讀取：

Rust Book Listing 20-11：可變 static 計數器
static mut COUNTER: u32 = 0;

/// SAFETY: Calling this from more than a single thread at a time is undefined
/// behavior, so you *must* guarantee you only call it from a single thread at
/// a time.
unsafe fn add_to_count(inc: u32) {
    unsafe {
        COUNTER += inc;
    }
}

fn main() {
    unsafe {
        // SAFETY: This is only called from a single thread in `main`.
        add_to_count(3);
        println!("COUNTER: {}", *(&raw const COUNTER));
    }
}

Miri 與 Rustonomicon

寫 unsafe 程式碼時，Rust Book 建議用官方工具 Miri 偵測未定義行為（undefined behavior）。它需要 nightly 版 Rust，用 cargo +nightly miri run 執行；官方示範用它檢查「在任意位址建立 10,000 個元素切片」的錯誤範例時，Miri 會回報 Undefined Behavior。如果想深入 unsafe，The Rustonomicon 是官方的進階參考：它假設讀者已熟悉 Rust 與基本系統程式設計，主題涵蓋（不安全）的意義、安全抽象技巧、subtyping 與 variance、panic 安全性等；該書自述尚未完整，且與 The Reference 若有出入，以 The Reference 為準。

小結

  • Box<T>：資料放堆積，指標大小固定，能讓遞迴型別有確定大小。
  • Rc<T>：參考計數的共享所有權，只限單執行緒、唯讀共享。
  • unsafe 不是關掉安全檢查，而是五種被明確標示的操作；最佳實務是縮小區塊、對外提供安全 API、寫 SAFETY 註解，並用 Miri 檢查。
