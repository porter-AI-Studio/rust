第 12 章 · Part 4：並行與非同步

無畏並行：執行緒、通道與共享狀態

所有權與型別系統不只管記憶體，也把大多數並行錯誤擋在編譯期。

Rust 官方文件（The Rust Programming Language，下稱 Rust Book）的說法是：Rust 團隊起初認為「確保記憶體安全」與「防止並行問題」是兩個需要不同方法的挑戰，後來發現所有權與型別系統能同時解決這兩類問題。結果是許多並行錯誤在 Rust 變成編譯期錯誤而非執行期錯誤，這就是「無畏並行」（fearless concurrency）。本章依序看三件事：建立執行緒、用通道傳訊息、用 Mutex 共享狀態，最後談 Send 與 Sync。除特別標明外，範例皆取自 Rust Book。

執行緒：spawn 與 join

多執行緒能提升效能，但也帶來複雜度。Rust Book 列出幾類常見問題：競態條件（race condition，執行緒以不一致的順序存取資料）、死結（deadlock，兩個執行緒互相等待）、以及只在特定情況發生、難以重現的 bug。Rust 標準函式庫採 1:1 模型，一個語言層級的執行緒對應一個作業系統執行緒；也有 crate 實作其他模型（官方並指出非同步是另一種並行做法，下一章會談）。

thread::spawn 接收一個閉包，在新執行緒執行。主執行緒結束時，所有被產生的執行緒會被強制關閉，不管它們有沒有跑完。要等它們完成，要保存 spawn 回傳的 JoinHandle，並呼叫 join，它會阻塞目前的執行緒直到對方結束：

Rust Book Listing 16-2：用 join 等待執行緒
use std::thread;
use std::time::Duration;

fn main() {
    let handle = thread::spawn(|| {
        for i in 1..10 {
            println!("hi number {i} from the spawned thread!");
            thread::sleep(Duration::from_millis(1));
        }
    });

    for i in 1..5 {
        println!("hi number {i} from the main thread!");
        thread::sleep(Duration::from_millis(1));
    }

    handle.join().unwrap();
}
Rust Book：輸出（每次執行順序可能不同）
hi number 1 from the main thread!
hi number 2 from the main thread!
hi number 1 from the spawned thread!
hi number 3 from the main thread!
hi number 2 from the spawned thread!
hi number 4 from the main thread!
hi number 3 from the spawned thread!
hi number 4 from the spawned thread!
hi number 5 from the spawned thread!
hi number 6 from the spawned thread!
hi number 7 from the spawned thread!
hi number 8 from the spawned thread!
hi number 9 from the spawned thread!

官方還示範：把 handle.join().unwrap() 移到主執行緒的 for 迴圈之前，輸出就不再交錯，因為主執行緒會先等衍生執行緒跑完。join 放的位置會影響執行緒是否真的同時執行。

move 閉包

想在衍生執行緒中使用主執行緒的資料，閉包預設只會借用，而 Rust 無法得知執行緒會活多久，所以編譯器拒絕下面的程式：

Rust Book Listing 16-3：閉包借用 v（無法編譯）
use std::thread;

fn main() {
    let v = vec![1, 2, 3];

    let handle = thread::spawn(|| {
        println!("Here's a vector: {v:?}");
    });

    handle.join().unwrap();
}
Rust Book：編譯器錯誤（節錄）
error[E0373]: closure may outlive the current function, but it borrows `v`, which is owned by the current function
 --> src/main.rs:6:32
  |
6 |     let handle = thread::spawn(|| {
  |                                ^^ may outlive borrowed value `v`
7 |         println!("Here's a vector: {v:?}");
  |                                     - `v` is borrowed here
  |
help: to force the closure to take ownership of `v` (and any other referenced variables), use the `move` keyword
  |
6 |     let handle = thread::spawn(move || {
  |                                ++++

照提示加上 move，讓閉包取得 v 的所有權：

Rust Book Listing 16-5：move 閉包
use std::thread;

fn main() {
    let v = vec![1, 2, 3];

    let handle = thread::spawn(move || {
        println!("Here's a vector: {v:?}");
    });

    handle.join().unwrap();
}

官方還有一個對照：若在衍生執行緒之後，主執行緒呼叫 drop(v)，就算用了 move 也會得到 E0382（使用已移動的值），因為所有權已經交給閉包。所有權規則在這裡擋下了潛在的使用已釋放資料問題。

通道：用訊息傳遞資料

Rust Book 引用 Go 語言文件的口號：不要透過共享記憶體來通訊，而要透過通訊來共享記憶體。標準函式庫提供的通道（channel）有發送端（transmitter，tx）與接收端（receiver，rx）兩半。mpsc 是 multiple producer, single consumer（多個生產者、單一消費者）的縮寫。recv 會阻塞直到收到值；try_recv 不阻塞，立刻回傳 Result。下例由衍生執行緒送出 "hi"，主執行緒印出 Got: hi：

Rust Book Listing 16-8：基本通道
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();

    thread::spawn(move || {
        let val = String::from("hi");
        tx.send(val).unwrap();
    });

    let received = rx.recv().unwrap();
    println!("Got: {received}");
}

所有權在這裡扮演關鍵角色。send 會取得參數的所有權，所以送出後再使用該值，編譯器直接報錯（官方輸出為 E0382）。如果允許，接收端執行緒可能在你繼續使用之前就修改或釋放它：

Rust Book Listing 16-9：送出後使用 val（無法編譯）
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();

    thread::spawn(move || {
        let val = String::from("hi");
        tx.send(val).unwrap();
        println!("val is {val}");
    });

    let received = rx.recv().unwrap();
    println!("Got: {received}");
}

要有多個生產者，就對發送端 clone，每個執行緒各拿一個。接收端可以直接當迭代器 for received in rx，通道關閉時迴圈結束。多個發送者的訊息到達順序取決於系統排程，官方明說每次執行順序可能不同：

Rust Book Listing 16-11：多個生產者
use std::sync::mpsc;
use std::thread;
use std::time::Duration;

fn main() {
    // --snip--
    let (tx, rx) = mpsc::channel();

    let tx1 = tx.clone();
    thread::spawn(move || {
        let vals = vec![
            String::from("hi"),
            String::from("from"),
            String::from("the"),
            String::from("thread"),
        ];

        for val in vals {
            tx1.send(val).unwrap();
            thread::sleep(Duration::from_secs(1));
        }
    });

    thread::spawn(move || {
        let vals = vec![
            String::from("more"),
            String::from("messages"),
            String::from("for"),
            String::from("you"),
        ];

        for val in vals {
            tx.send(val).unwrap();
            thread::sleep(Duration::from_secs(1));
        }
    });

    for received in rx {
        println!("Got: {received}");
    }
    // --snip--
}

共享狀態：Mutex 與 Arc

通道類似單一所有權，值送出就不該再用；共享記憶體則像多重所有權，多個執行緒同時存取同一份資料。Mutex（mutual exclusion，互斥鎖）一次只允許一個執行緒存取資料。使用規則有兩條：用資料前必須先取得鎖；用完必須解鎖。Rust Book 說明，由於型別系統與所有權規則，你不會在「上鎖與解鎖」上出錯。

lock 回傳包在 LockResult 中的 MutexGuard，它實作 Deref 指向內部資料，並在離開作用域時自動解鎖。若持有鎖的另一個執行緒 panic，lock 會失敗，因此範例用 unwrap：

Rust Book Listing 16-12：單執行緒下的 Mutex
use std::sync::Mutex;

fn main() {
    let m = Mutex::new(5);

    {
        let mut num = m.lock().unwrap();
        *num = 6;
    }

    println!("m = {m:?}");
}

從 Rc 到 Arc

要讓十個執行緒各把計數器加一，把 Mutex 的所有權 move 進迴圈中的每個閉包是不行的，編譯器回報 counter 在上一輪已被移動。上一章的 Rc<T> 能提供多重所有權，但換成 Rc<Mutex<i32>> 後會得到新的錯誤：

Rust Book：Rc 無法跨執行緒（節錄）
error[E0277]: `Rc<std::sync::Mutex<i32>>` cannot be sent between threads safely
  --> src/main.rs:11:36
   = help: within `{closure@src/main.rs:11:36: 11:43}`, the trait `Send` is not implemented for `Rc<std::sync::Mutex<i32>>`

原因是 Rc<T> 管理參考計數時沒有使用並行原語，計數可能被其他執行緒打斷而算錯，導致記憶體洩漏或資料被提早釋放。解法是 Arc<T>（atomically reference-counted，原子參考計數），它與 Rc 的 API 相同，但以原子操作維護計數。為什麼不是所有型別預設就用 Arc？官方答案是執行緒安全有效能代價，只在需要時才付出。

Rust Book Listing 16-15：Arc 與 Mutex 搭配
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0));
    let mut handles = vec![];

    for _ in 0..10 {
        let counter = Arc::clone(&counter);
        let handle = thread::spawn(move || {
            let mut num = counter.lock().unwrap();

            *num += 1;
        });
        handles.push(handle);
    }

    for handle in handles {
        handle.join().unwrap();
    }

    println!("Result: {}", *counter.lock().unwrap());
}

此程式輸出 Result: 10。官方補充：做簡單數值運算時，標準函式庫 std::sync::atomic 有比 Mutex 更簡單的型別。另外，Mutex 和 RefCell 一樣提供內部可變性（interior mutability）：Arc<Mutex<T>> 之於多執行緒，就像 Rc<RefCell<T>> 之於單執行緒。

⚠️
編譯器擋不住的邏輯錯誤

Rust Book 提醒：Rc<T> 有參考循環造成記憶體洩漏的風險，同樣地，Mutex<T> 有死結風險：兩個執行緒各持有一把鎖，並互相等待對方的鎖。Rust 無法在編譯期替你防止死結。

Send 與 Sync

上面 Rc 的錯誤訊息提到 Send trait。這兩個 marker trait 是 Rust 並行保證的基礎（以下取自官方文件 doc.rust-lang.org/book/ch16-04-extensible-concurrency-sync-and-send.html，本章主要素材未涵蓋此節，為上網補充）：

  • Send：此型別的值的所有權可以在執行緒之間轉移。Rc<T> 不是 Send，因為複製後交給另一個執行緒，兩邊可能同時更新參考計數；Arc<T> 是。
  • Sync：此型別可以安全地被多個執行緒參考（等價於 &T 是 Send）。Mutex<T> 是 Sync；RefCell<T> 與 Cell<T> 不是，因為執行期借用檢查不是執行緒安全的。
  • 它們是自動推導的：完全由 Send 型別組成的型別也自動是 Send。它們沒有方法，只用來強制並行相關的不變式。手動實作它們需要 unsafe（上一章的「實作 unsafe trait」就是這種情況）。

小結

  • thread::spawn + join 建立並等待執行緒；跨執行緒使用資料要 move。
  • 通道傳遞所有權，送出後不能再用；tx.clone() 可做多生產者。
  • Arc<Mutex<T>> 是共享可變狀態的標準組合；Rc 因不是 Send 被編譯器擋下。
  • 編譯器能擋資料競爭，但擋不了死結等邏輯錯誤。
