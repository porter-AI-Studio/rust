第 9 章 · Part 3：型別系統與錯誤處理

錯誤處理：Result、panic 與測試

把「可能失敗」寫進回傳型別，讓編譯器的型別檢查與警告促使你檢視失敗路徑，再用測試證明你處理對了。

寫過 TypeScript 的人，對 try/catch 一定不陌生：任何函式都可能丟出例外，但函式簽名完全不會告訴你。Rust 沒有例外機制，它把錯誤分成兩類：可以恢復的錯誤用 Result<T, E> 回傳，無法恢復的錯誤用 panic! 讓程式停下來。本章依序談 Result 的各種處理方式、? 運算子、什麼時候該 panic、自訂錯誤型別的常見做法，最後用 Rust 內建的測試功能驗證這些行為。本章範例除特別標明外，皆取自 Rust 官方文件 The Rust Programming Language（以下簡稱 Rust Book）。

Result：把失敗放進回傳型別

Result 是一個只有兩個變體的列舉，Ok 裝成功的值，Err 裝錯誤資訊。T 與 E 是泛型參數，下一章會詳細說明。像 File::open 這類可能失敗的函式，回傳型別就是 Result<std::fs::File, std::io::Error>，呼叫端不處理就拿不到檔案控制代碼。

最基本的處理方式是 match。官方範例讓檔案不存在時（ErrorKind::NotFound）建立新檔，其他錯誤才 panic：

Rust Book Listing 9-5：依錯誤種類分別處理
use std::fs::File;
use std::io::ErrorKind;

fn main() {
    let greeting_file_result = File::open("hello.txt");

    let greeting_file = match greeting_file_result {
        Ok(file) => file,
        Err(error) => match error.kind() {
            ErrorKind::NotFound => match File::create("hello.txt") {
                Ok(fc) => fc,
                Err(e) => panic!("Problem creating the file: {e:?}"),
            },
            _ => {
                panic!("Problem opening the file: {error:?}");
            }
        },
    };
}

巢狀 match 很囉唆。Rust Book 指出 Result 有許多搭配閉包使用的方法，可以寫得更精簡（閉包在下一章介紹）：

Rust Book：用 unwrap_or_else 改寫，行為與 Listing 9-5 相同
use std::fs::File;
use std::io::ErrorKind;

fn main() {
    let greeting_file = File::open("hello.txt").unwrap_or_else(|error| {
        if error.kind() == ErrorKind::NotFound {
            File::create("hello.txt").unwrap_or_else(|error| {
                panic!("Problem creating the file: {error:?}");
            })
        } else {
            panic!("Problem opening the file: {error:?}");
        }
    });
}

unwrap 與 expect：明知會 panic 的捷徑

unwrap 在 Ok 時回傳內部的值，在 Err 時直接 panic!。expect 做同樣的事，但可以自訂 panic 訊息。Rust Book 的說法是：在正式品質的程式碼裡，多數 Rustacean 會選 expect 並寫清楚「為什麼這裡應該永遠成功」，這樣假設被推翻時，除錯資訊比較完整。

Rust Book：expect 自訂 panic 訊息
use std::fs::File;

fn main() {
    let greeting_file = File::open("hello.txt")
        .expect("hello.txt should be included in this project");
}

錯誤傳播與 ? 運算子

函式內部呼叫了可能失敗的操作時，常見做法不是自己處理，而是把錯誤交給呼叫端決定，這叫錯誤傳播（propagating）。先看手動寫法，用 match 提早 return Err(e)：

Rust Book Listing 9-6：用 match 傳播錯誤
use std::fs::File;
use std::io::{self, Read};

fn read_username_from_file() -> Result<String, io::Error> {
    let username_file_result = File::open("hello.txt");

    let mut username_file = match username_file_result {
        Ok(file) => file,
        Err(e) => return Err(e),
    };

    let mut username = String::new();

    match username_file.read_to_string(&mut username) {
        Ok(_) => Ok(username),
        Err(e) => Err(e),
    }
}

這個模式太常見，Rust 提供 ? 運算子。? 放在 Result 後面：值是 Ok 就取出內部的值繼續執行；是 Err 就當作 return 讓整個函式提早回傳該錯誤。

Rust Book Listing 9-7：用 ? 運算子
use std::fs::File;
use std::io::{self, Read};

fn read_username_from_file() -> Result<String, io::Error> {
    let mut username_file = File::open("hello.txt")?;
    let mut username = String::new();
    username_file.read_to_string(&mut username)?;
    Ok(username)
}

還可以在 ? 之後直接串接方法呼叫，Rust Book 的 Listing 9-8 如下：

Rust Book Listing 9-8：? 之後串接方法
use std::fs::File;
use std::io::{self, Read};

fn read_username_from_file() -> Result<String, io::Error> {
    let mut username = String::new();

    File::open("hello.txt")?.read_to_string(&mut username)?;

    Ok(username)
}

讀檔成字串太常用，標準函式庫其實有 fs::read_to_string，一行就能完成（Listing 9-9）：

Rust Book Listing 9-9
use std::fs;
use std::io;

fn read_username_from_file() -> Result<String, io::Error> {
    fs::read_to_string("hello.txt")
}
ℹ️
? 與 match 的差別：From 轉換

被 ? 處理的錯誤值會經過標準函式庫 From trait 的 from 函式，轉換成目前函式回傳型別所宣告的錯誤型別。Rust Book 舉例：若自訂 OurError 並實作 impl From<io::Error> for OurError，函式內的 ? 就會自動轉換，不必多寫程式碼。這是下面自訂錯誤型別的基礎。

? 能用在哪裡

? 只能用在回傳型別與它相容的函式裡。如果在回傳 () 的 main 裡對 File::open 使用 ?，編譯器會報錯（Rust Book 的輸出節錄）：

Rust Book Listing 9-10 的編譯錯誤（節錄）
error[E0277]: the `?` operator can only be used in a function that returns `Result` or `Option` (or another type that implements `FromResidual`)
 --> src/main.rs:4:48
  |
3 | fn main() {
  | --------- this function should return `Result` or `Option` to accept `?`
4 |     let greeting_file = File::open("hello.txt")?;
  |                                                ^ cannot use the `?` operator in a function that returns `()`

解法有兩種：把函式回傳型別改成相容的型別，或用 match／Result 的方法就地處理。? 也能用在 Option：遇到 None 就提早回傳 None。但 Result 與 Option 不會自動互轉，需要的話用 Result 的 ok 方法或 Option 的 ok_or 方法明確轉換。

Rust Book Listing 9-11：對 Option 使用 ?
fn last_char_of_first_line(text: &str) -> Option<char> {
    text.lines().next()?.chars().last()
}

fn main() {
    assert_eq!(
        last_char_of_first_line("Hello, world\nHow are you today?"),
        Some('d')
    );

    assert_eq!(last_char_of_first_line(""), None);
    assert_eq!(last_char_of_first_line("\nhi"), None);
}

想在 main 裡使用 ?，可以讓 main 回傳 Result<(), Box<dyn Error>>。Box<dyn Error> 在 Rust Book 中被解釋為「任何一種錯誤」，這是 trait object，後續章節會再談。main 回傳 Ok(()) 時程式以 0 結束，回傳 Err 時以非零值結束，與 C 程式的慣例一致。

Rust Book Listing 9-12：main 回傳 Result
use std::error::Error;
use std::fs::File;

fn main() -> Result<(), Box<dyn Error>> {
    let greeting_file = File::open("hello.txt")?;

    Ok(())
}

panic 還是 Result：怎麼決定

Rust Book 的建議是：定義可能失敗的函式時，回傳 Result 是好的預設選擇，因為你把「這個錯誤能不能恢復」的決定權交給呼叫端；一旦 panic，呼叫端就沒有選擇了。以下情境適合 panic（或 unwrap／expect）：

  • 範例、原型與測試：範例裡的 unwrap 代表「這裡之後要換成真正的錯誤處理」；測試中的 panic 本來就是標記失敗的方式。
  • 你比編譯器掌握更多資訊：例如解析寫死的合法 IP 字串，編譯器仍會要求處理 Result，這時用 expect 並寫明理由。
  • 違反契約或可能造成安全風險：標準函式庫在越界存取記憶體時 panic，就是因為這是常見的安全問題，且代表呼叫端程式有 bug。
Rust Book：明確知道字串合法時用 expect 並寫明理由
fn main() {
    use std::net::IpAddr;

    let home: IpAddr = "127.0.0.1"
        .parse()
        .expect("Hardcoded IP address should be valid");
}

相反地，預期會發生的失敗（Rust Book 舉例：解析器收到格式錯誤的資料、HTTP 請求回傳表示被限速的狀態）應該回傳 Result。

用型別取代執行期檢查

Rust Book 進一步建議善用型別系統：參數若是具體型別而非 Option，函式內就不必處理 None；用 u32 就保證不是負數。更進一步，可以建立自訂型別，只在建構函式驗證一次。下面的 Guess 欄位是私有的，外部只能透過 Guess::new 建立，因此任何拿到 Guess 的函式都能確信值在 1 到 100 之間：

Rust Book Listing 9-13：Guess 型別
pub struct Guess {
    value: i32,
}

impl Guess {
    pub fn new(value: i32) -> Guess {
        if value < 1 || value > 100 {
            panic!("Guess value must be between 1 and 100, got {value}.");
        }

        Guess { value }
    }

    pub fn value(&self) -> i32 {
        self.value
    }
}

自訂錯誤型別：thiserror 與 anyhow

當函式可能因為多種原因失敗時，常見做法是定義一個列舉，每個變體代表一類錯誤，並實作 From 讓 ? 自動轉換。社群有兩個常用 crate 簡化這件事。下面取自一份第三方整理的 Rust 慣用模式文件（ECC 的 rust-patterns skill，簡體中文版），其建議是：函式庫用 thiserror 定義具型別的錯誤，應用程式用 anyhow 做彈性的錯誤處理。#[from] 屬性會產生對應的 From 轉換。

取自 ECC rust-patterns 素材（第三方整理，非官方文件）
// Library code: structured, typed errors
use thiserror::Error;

#[derive(Debug, Error)]
pub enum StorageError {
    #[error("record not found: {id}")]
    NotFound { id: String },
    #[error("connection failed")]
    Connection(#[from] std::io::Error),
    #[error("invalid data: {0}")]
    InvalidData(String),
}

// Application code: flexible error handling
use anyhow::{bail, Result};

fn run() -> Result<()> {
    let config = load_config("app.toml")?;
    if config.workers == 0 {
        bail!("worker count must be > 0");
    }
    Ok(())
}
⚠️
範例不是完整可編譯程式

上例中的 load_config 與 config.workers 在素材另一段定義，這裡沒有收錄；thiserror 與 anyhow 的 API 細節本章未另行查證官方文件（docs.rs），實際使用前請以其文件為準。

用測試驗證錯誤處理

測試就是以 #[test] 標記的函式，通常做三件事：準備資料、執行要測的程式碼、斷言結果。cargo new adder --lib 建立函式庫專案時，會自動產生 tests 模組與一個範例測試：

Rust Book Listing 11-1：cargo new 自動產生的測試
pub fn add(left: u64, right: u64) -> u64 {
    left + right
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn it_works() {
        let result = add(2, 2);
        assert_eq!(result, 4);
    }
}

用 cargo test 執行，每個測試會在新的執行緒中跑，只要該執行緒 panic 就標記為失敗：

Rust Book Listing 11-2：cargo test 輸出（略去 Doc-tests 區段）
$ cargo test
   Compiling adder v0.1.0 (file:///projects/adder)
    Finished `test` profile [unoptimized + debuginfo] target(s) in 0.57s
     Running unittests src/lib.rs (target/debug/deps/adder-01ad14159ff659ab)

running 1 test
test tests::it_works ... ok

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s

斷言巨集

assert! 檢查布林條件，assert_eq! 與 assert_ne! 比較兩個值是否相等、不相等。它們用 == 與 != 比較，失敗時以除錯格式印出兩邊的值，所以比較的型別必須實作 PartialEq 與 Debug。Rust 稱兩邊為 left 與 right，不分「預期值」與「實際值」，順序不影響結果。失敗時的輸出像這樣：

Rust Book：assert_eq! 失敗輸出（節錄）
---- tests::it_adds_two stdout ----
thread 'tests::it_adds_two' (6020955) panicked at src/lib.rs:12:9:
assertion `left == right` failed
  left: 5
 right: 4

這三個巨集都可以在必要參數之後附上自訂訊息，內容會交給 format! 處理。

should_panic：測試「應該失敗」的路徑

回到前面的 Guess，要驗證超出範圍時真的會 panic，可以在 #[test] 後面加 #[should_panic]。單用 should_panic 不夠精確，因為其他原因造成的 panic 也會通過；加上 expected 參數，測試會檢查 panic 訊息是否包含指定的子字串：

Rust Book Listing 11-9：should_panic 搭配 expected
pub struct Guess {
    value: i32,
}

impl Guess {
    pub fn new(value: i32) -> Guess {
        if value < 1 {
            panic!(
                "Guess value must be greater than or equal to 1, got {value}."
            );
        } else if value > 100 {
            panic!(
                "Guess value must be less than or equal to 100, got {value}."
            );
        }

        Guess { value }
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    #[should_panic(expected = "less than or equal to 100")]
    fn greater_than_100() {
        Guess::new(200);
    }
}

測試也可以回傳 Result

測試函式可以改成回傳 Result<T, E>，這樣就能在測試內使用 ?，任何一步回傳 Err 都會讓測試失敗。限制是：這種測試不能搭配 #[should_panic]；要斷言某個操作回傳 Err，請用 assert!(value.is_err())，而不要對它使用 ?。

Rust Book：測試回傳 Result
pub fn add(left: u64, right: u64) -> u64 {
    left + right
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn it_works() -> Result<(), String> {
        let result = add(2, 2);
        if result == 4 {
            Ok(())
        } else {
            Err(String::from("two plus two does not equal four"))
        }
    }
}

小結

  • Result 把失敗寫進型別，? 讓錯誤傳播只要一個字元，並透過 From 自動轉換錯誤型別。
  • 預設回傳 Result；範例、原型、測試、以及你有編譯器看不到的保證時才用 unwrap／expect；違反契約時 panic。
  • 用自訂型別把驗證集中在建構函式，函式簽名就成為文件。
  • #[test]、assert_eq!、should_panic 是驗證錯誤路徑的基本工具。

本章多次提到泛型 Result<T, E> 與閉包（unwrap_or_else）、From trait，下一章「Trait、泛型、閉包與迭代器」會逐一說明它們如何運作。
