第 8 章 · Part 2：所有權：Rust 的核心

給 TypeScript 開發者的所有權對照

你已經知道「物件賦值是共享參考」；Rust 只是把這件事變成編譯器要管的契約。

前三章把所有權、借用與生命週期講完了。如果你的背景是 TypeScript，這一章替你把這些概念接到熟悉的地方：同樣一個動作，在 TS 與 Rust 各自代表什麼。

ℹ️
本章素材與限制

Rust 範例取自 dev.to 上 Rahul 的系列文〈Ownership in Rust for Typescript devs〉（2024-09-28，個人部落格，非官方）、ZetCode 的 Rust ownership and borrowing，以及 iT 邦幫忙 2025 鐵人賽〈(Day3) Rust 借用 (Borrowing)：有契約的共享〉。其中 Rahul 這篇雖以 TypeScript 開發者為對象，內文並沒有附 TypeScript 程式碼，因此本章的 TS 片段都是本書自擬的對照範例，會明確標示。stub 原先預告的 readonly 與「ownership transfer pattern」等對照，素材未提供，本章不展開。

先建立心智模型：誰負責收垃圾？

在 TS 裡，你建立物件後幾乎不用想它什麼時候被回收；Rahul 的文章說，所有權讓你不需要垃圾回收器也不需要手動管理記憶體，同時避免資料競爭、空指標解參考、懸空指標等常見錯誤。兩者的差別整理如下：

面向TypeScript／JavaScriptRust
記憶體回收執行期由垃圾回收器處理擁有者離開作用域時自動 drop，規則在編譯期檢查
物件賦值 b = a兩個變數共享同一份資料所有權移動，a 失效
想要明確複製資料自己寫複製邏輯明確呼叫 clone()（複製的語意與成本由型別的 Clone 實作決定）
共享資料給別人用直接傳遞，誰都能改借用：&T 唯讀、&mut T 獨佔可寫
引用懸空由 GC 保證物件存活到不再被引用編譯器以生命週期檢查，違反就不給編譯

賦值：從「共享」變成「過戶」

iT 邦幫忙的文章指出，在 Python 或 JavaScript 裡，共享是隱式的：你不知道有多少參考指向同一份資料，也不知道誰會在什麼時候修改它。對應到 TS，大概像這樣：

TypeScript：賦值只是多一個參考（本書自擬）
// 本書自擬的 TypeScript 對照（素材未提供 TS 程式碼）
const a = [1, 2, 3];
const b = a;          // 沒有複製，b 與 a 指向同一個陣列
b.push(4);
console.log(a);       // [1, 2, 3, 4]：a 也被改到了

同樣的動作在 Rust，Rahul 的文章這麼寫：把一個值從一個變數賦給另一個，所有權就從原變數移到新變數，原變數不能再用。官方 Rust Book 也說明了原因：String 的資料在堆積上，移動並使原變數失效，才能避免兩個變數都去釋放同一塊記憶體（雙重釋放）。

Rust：賦值就是移動（Rahul，dev.to）
let s1 = String::from("hello");
let s2 = s1; // Ownership of the string moves from `s1` to `s2`
// `s1` is no longer valid here

你若想兩邊都保留，就明確要求複製：

Rust：clone 明確複製資料，以 String 為例（Rahul，dev.to）
let s1 = String::from("hello");
let s2 = s1.clone(); // `s2` is a deep copy of `s1`
// Both `s1` and `s2` are valid here

文章提醒 clone 有效能成本，因為要複製資料。對 TS 開發者來說，這恰好補上一個你平常看不見的成本：在 TS 裡複製大型物件的代價藏在你自己寫的複製函式裡；在 Rust，複製永遠以 .clone() 的形式顯現在程式碼上。

為什麼 number 不會「被搬走」？

TS 開發者常有疑問：既然 let y = x 會移動，為什麼數字賦值後原變數還能用？因為純放在堆疊的簡單型別實作了 Copy，賦值時是逐位元複製。ZetCode 的文章列出：所有整數型別、浮點數型別、bool、char，以及成員全是 Copy 的 tuple；而管理堆積記憶體的型別如 String、Vec<T> 則不是。

Rust：Copy 型別賦值後仍可用（ZetCode）
fn main() {
    let x: i32 = 5;
    let y = x;          // x is copied, not moved

    println!("x = {}, y = {}", x, y);

    let flag = true;
    let other = flag;   // bool is Copy too

    println!("flag = {}, other = {}", flag, other);
}
💡
用 TS 的直覺記

TS 的原始型別（數字、布林）賦值時本來就是複製值；物件則是共享。Rust 把這條界線改畫在「有沒有 Copy」：簡單、在堆疊上的值複製，會管理堆積資源的值移動。（此類比為本書歸納，並非素材原文。）

傳給函式：參數也會被「吃掉」

在 TS，把物件傳給函式後，呼叫端照樣能用。在 Rust，傳入 String 就是移動：函式取得所有權，結束時資料被 drop，呼叫端的變數失效。

Rust：函式取得所有權（Rahul，dev.to）
fn takes_ownership(s: String) {
    println!("{}", s);
} // `s` is dropped here

let s1 = String::from("hello");
takes_ownership(s1); // `s1` is moved to the function and is no longer valid here

文章也說明，想把所有權交還給呼叫端就得回傳它（這個模式在第 5 章已經看過，並指出太囉嗦）。更好的方式是借用。

借用：&T 像唯讀視圖，&mut T 像獨佔的寫入權

Rust：借用，不移動所有權（Rahul，dev.to）
fn borrow_string(s: &String) {
    println!("{}", s);
}

let s1 = String::from("hello");
borrow_string(&s1); // Borrow `s1` without moving ownership
// `s1` is still valid here
Rust：可變借用（Rahul，dev.to）
fn modify_string(s: &mut String) {
    s.push_str(", world");
}

let mut s1 = String::from("hello");
modify_string(&mut s1); // Borrow `s1` mutably
println!("{}", s1); // Output: "hello, world"

與 TS 最大的差別，在於 Rust 把「誰能改」這件事寫進型別與簽名：&T 表示我只想讀、&mut T 表示我需要修改、T 表示我要取得所有權（iT 邦幫忙文章的歸納）。TS 的 const 管的是「變數綁定不能重新指派」，不是物件內容能不能改，兩者不是同一件事；Rust 的 mut 與參考種類才是在管內容能不能改。這段對 const 的說明是 TS 本身的語言行為，素材沒有明講，請自行對照。

代價是 Rahul 與官方都提到的規則：同一時間，要嘛一個可變參考，要嘛任意多個不可變參考，不能兩者並存。iT 邦幫忙的文章用它和 Go 做對照：Go 讓共享變顯式，但編譯器擋不住 data race；Rust 在編譯期就擋掉。

Rust：不能同時有兩個可變借用（iT 邦幫忙，註解為原文）
let mut data = vec![1, 2, 3];
let ptr1 = &mut data;
// let ptr2 = &mut data;  // ❌ 編譯錯誤！不能同時有兩個可變借用

ptr1[0] = 999;
println!("{:?}", data);  // [999, 2, 3]

懸空參考：TS 開發者最少遇到的問題

在 GC 語言中，只要還有人引用物件，物件就不會被回收，所以你幾乎沒機會遇到懸空引用。Rust 則允許資料先離開作用域，所以需要檢查：

Rust：懸空參考被 borrow checker 擋下（Rahul，dev.to）
let r;
{
    let s = String::from("hello");
    r = &s; // Error: `s` does not live long enough
}
// `r` would be a dangling reference here

在這個例子中，s 在內層區塊結束時被銷毀，r 卻還想用它，編譯器會在編譯期攔下來。這就是第 7 章生命週期要解決的事。

三個常見的思維轉換

  1. 先想「誰擁有它」，再決定怎麼傳。函式只是要讀就傳 &T，要改就傳 &mut T，真的要接手資料才傳 T。
  2. 看到 .clone() 要想一下成本。它是「複製堆積資料」的明示標記；在 Rust 裡，自動發生的複製都很便宜，昂貴的複製一定要你親手寫。
  3. 把編譯器的借用錯誤當成早期 bug 報告。官方文件的說法是：借用錯誤雖然令人沮喪，但那是編譯器在編譯期就指出潛在的 bug，並告訴你問題在哪裡，你不必在執行期追查資料為什麼不是你以為的樣子。
⚠️
素材一致性提醒

Rahul 的文章在敘述 takes_ownership 時，沿用「s1 移入函式、函式結束時被 drop」的說法，與官方 Rust Book 一致；兩份素材在所有權規則上沒有互相矛盾之處。但該文的範例沒有 fn main() 包裝，是片段，不能直接貼進專案編譯。

💡
本章重點回顧

TS 的賦值是共享、由 GC 兜底；Rust 的賦值是移動、由編譯器兜底。想要共享請用借用，想要明確複製請 clone，簡單的堆疊型別則自動 Copy。
