第 15 章 · Part 5：工程實務與生態

慣用寫法與小型專案

用明確型別、測試與文件建立可維護的 Rust 專案，並了解 crate 發布流程。

前面各章教的是語言本身；這一章看「Rust 程式設計師平常怎麼寫」：慣用模式、測試、文件與發佈。慣用模式的主要素材是 ECC 專案裡的 rust-patterns 技能文件（GitHub 上的社群文件，原文為簡體中文，非官方），測試、文件與發佈則取自官方 Rust Book。

慣用模式

該文件把慣用做法歸納為六個領域：所有權與借用、Result／? 錯誤傳播、列舉與窮盡匹配、trait 與泛型、並發、依領域組織且最小化 pub 的模組結構。以下挑幾個最常用的。

錯誤處理：用 ? 傳遞，不在正式環境 unwrap

文件的建議：錯誤要帶著上下文往上傳，不要在生產程式碼裡 unwrap()。

rust-patterns 文件範例
// Good: Propagate errors with context
use anyhow::{Context, Result};

fn load_config(path: &str) -> Result<Config> {
    let content = std::fs::read_to_string(path)
        .with_context(|| format!("failed to read config from {path}"))?;
    let config: Config = toml::from_str(&content)
        .with_context(|| format!("failed to parse config from {path}"))?;
    Ok(config)
}

// Bad: Panics on error
fn load_config_bad(path: &str) -> Config {
    let content = std::fs::read_to_string(path).unwrap(); // Panics!
    toml::from_str(&content).unwrap()
}

另一條規則：函式庫用 thiserror 定義結構化、有型別的錯誤；應用程式用 anyhow 做彈性處理（錯誤處理的基礎見第 9 章）。

rust-patterns 文件範例
// Library code: structured, typed errors
use thiserror::Error;

#[derive(Debug, Error)]
pub enum StorageError {
    #[error("record not found: {id}")]
    NotFound { id: String },
    #[error("connection failed")]
    Connection(#[from] std::io::Error),
    #[error("invalid data: {0}")]
    InvalidData(String),
}

// Application code: flexible error handling
use anyhow::{bail, Result};

fn run() -> Result<()> {
    let config = load_config("app.toml")?;
    if config.workers == 0 {
        bail!("worker count must be > 0");
    }
    Ok(())
}

讓非法狀態無法表示，且窮盡匹配

用列舉建模狀態，每個變體只帶合法狀態才有的資料。文件也建議：業務邏輯的 match 不要用萬用 _，這樣新增變體時編譯器會逼你處理，而不是被默默忽略。

rust-patterns 文件範例
// Good: Impossible states are unrepresentable
enum ConnectionState {
    Disconnected,
    Connecting { attempt: u32 },
    Connected { session_id: String },
    Failed { reason: String, retries: u32 },
}

fn handle(state: &ConnectionState) {
    match state {
        ConnectionState::Disconnected => connect(),
        ConnectionState::Connecting { attempt } if *attempt > 3 => abort(),
        ConnectionState::Connecting { .. } => wait(),
        ConnectionState::Connected { session_id } => use_session(session_id),
        ConnectionState::Failed { retries, .. } if *retries < 5 => retry(),
        ConnectionState::Failed { reason, .. } => log_failure(reason),
    }
}

Newtype 與 Builder

Newtype 把基本型別包成獨立型別，避免參數對調：

rust-patterns 文件範例
// Good: Distinct types prevent mixing up arguments
struct UserId(u64);
struct OrderId(u64);

fn get_order(user: UserId, order: OrderId) -> Result<Order> {
    // Can't accidentally swap user and order IDs
    todo!()
}

// Bad: Easy to swap arguments
fn get_order_bad(user_id: u64, order_id: u64) -> Result<Order> {
    todo!()
}

建構子參數多時用 Builder 模式：

rust-patterns 文件範例
struct ServerConfig {
    host: String,
    port: u16,
    max_connections: usize,
}

impl ServerConfig {
    fn builder(host: impl Into<String>, port: u16) -> ServerConfigBuilder {
        ServerConfigBuilder { host: host.into(), port, max_connections: 100 }
    }
}

struct ServerConfigBuilder { host: String, port: u16, max_connections: usize }

impl ServerConfigBuilder {
    fn max_connections(mut self, n: usize) -> Self { self.max_connections = n; self }
    fn build(self) -> ServerConfig {
        ServerConfig { host: self.host, port: self.port, max_connections: self.max_connections }
    }
}

// Usage: ServerConfig::builder("localhost", 8080).max_connections(200).build()
ℹ️
素材沒有的部分

大綱預告的 type state、封裝 unsafe 的完整手法、Clippy 規則細節與 CI 整合，素材未提供對應說明。該文件對 unsafe 只給出原則：有 Safety 說明、FFI 邊界或有正確性依據的效能路徑可以用；用來繞過借用檢查器、圖方便、沒寫 Safety 註解、轉型不相關型別則不行。

迭代器優先，其他速記

rust-patterns 文件範例
// Good: Declarative, lazy, composable
let active_emails: Vec<String> = users.iter()
    .filter(|u| u.is_active)
    .map(|u| u.email.clone())
    .collect();

// Bad: Imperative accumulation
let mut active_emails = Vec::new();
for user in &users {
    if user.is_active {
        active_emails.push(user.email.clone());
    }
}

文件的速查表還有：借用而非克隆、? 優於 unwrap()、對 Result 用 #[must_use]、用 Cow 避免不必要的分配、內部 API 用 pub(crate)。反模式則包含在 async 裡呼叫 std::thread::sleep 阻塞執行器（見第 13 章）。

專案結構與工具

文件建議按「領域」而不是按「型別」組織模組，並把 tests/、benches/ 放在專案根目錄：

測試

依官方 Rust Book，測試是用 #[test] 標註的函式，本體通常做三件事：準備資料、執行要測的程式、斷言結果。用 Cargo 建立函式庫專案時會自動產生測試模組：

官方 Rust Book Listing 11-1（cargo new adder --lib 產生）
pub fn add(left: u64, right: u64) -> u64 {
    left + right
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn it_works() {
        let result = add(2, 2);
        assert_eq!(result, 4);
    }
}

執行 cargo test 的輸出（官方書 Listing 11-2）：

官方 Rust Book Listing 11-2
$ cargo test
   Compiling adder v0.1.0 (file:///projects/adder)
    Finished `test` profile [unoptimized + debuginfo] target(s) in 0.57s
     Running unittests src/lib.rs (target/debug/deps/adder-01ad14159ff659ab)

running 1 test
test tests::it_works ... ok

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s

   Doc-tests adder

running 0 tests

test result: ok. 0 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s

官方書說明：測試失敗的條件是測試函式 panic，每個測試在新執行緒中執行，主執行緒看到測試執行緒死亡就標記失敗。assert! 檢查條件是否為 true，assert_eq! 檢查相等。輸出中的 Doc-tests 區段則是文件測試的結果。

文件與發佈到 crates.io

文件註解用三個斜線 ///，支援 Markdown；cargo doc --open 會產生 HTML 文件。註解裡的程式碼區塊也會在 cargo test 時當成測試執行，讓文件與程式碼保持同步。//! 則是替「包含它的項目」（例如整個 crate）寫文件。

官方 Rust Book Listing 14-1（文件註解與文件測試）
/// Adds one to the number given.
///
/// # Examples
///
/// ```
/// let arg = 5;
/// let answer = my_crate::add_one(arg);
///
/// assert_eq!(6, answer);
/// ```

發佈流程（官方書）：先用 GitHub 帳號登入 crates.io 取得 API token，再執行 cargo login，token 會存到 ~/.cargo/credentials.toml，這是機密，不可分享。crate 名稱先搶先贏。Cargo.toml 至少要有 description 與 license，否則 cargo publish 會報 400 錯誤。許多 Rust 社群專案採用 MIT OR Apache-2.0 雙授權。

可發佈的 Cargo.toml（官方 Rust Book）
[package]
name = "guessing_game"
version = "0.1.0"
edition = "2024"
description = "A fun game where you guess what number the computer has chosen."
license = "MIT OR Apache-2.0"

[dependencies]
發佈與撤回指令（官方 Rust Book 摘錄）
$ cargo login
$ cargo publish
$ cargo yank --vers 1.0.1
$ cargo yank --vers 1.0.1 --undo
⚠️
發佈是永久的

官方書強調：同一版本不能被覆寫，程式碼除非特殊情況也不能刪除，因為 crates.io 要當成永久的程式碼檔案庫，確保依賴它的專案持續可建置。有問題的版本可以用 cargo yank 阻止新專案依賴，已有 Cargo.lock 的專案不受影響；加上 --undo 可還原。

小型專案：命令列工具

官方 Rust Book 第 12 章拿「簡易版 grep」整合前面的概念：程式碼組織、向量與字串、錯誤處理、trait 與生命週期、測試。它也示範讀取環境變數來設定行為，並把錯誤訊息輸出到 stderr 而非 stdout，讓使用者可以把成功輸出導向檔案、同時仍在畫面看到錯誤。官方也提到社群成員 Andrew Gallant 寫的完整高速版本 ripgrep。本章素材只有該章的開場說明，沒有逐步實作的程式碼，所以這裡不編造完整實作，建議直接讀官方書第 12 章。
