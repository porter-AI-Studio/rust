現實檢查：批評、代價與重寫案例

比較 Rust 的實際代價與採用案例，區分量測、廠商自述及二手轉述，避免把個案效益當成普遍結論。

前面十六章多半在說 Rust 能做什麼。最後一章要把天平扳回來：批評者怎麼說、Rust 專案自己承認什麼、以及三個「從別的語言重寫成 Rust」的案例（Discord、Cloudflare、Momento）真正換來了什麼、付出了什麼。每一則說法都標示來源類型，因為這個主題最容易把行銷、立場與數據混在一起。

⚠️
素材限制

大綱預告的「編譯速度實測」「增量編譯瓶頸」「學習曲線量化」「導入檢核表」，本章素材都沒有提供自己的量測數字；以下只引用來源裡有的說法，沒有的就寫「素材未提供」，不另外編造。

批評者的聲音

第一份素材是 byteiota（作者署名 ByteBot）2025-11-24 的文章，內容是轉述並評論開發者 Bykozy 那篇廣為流傳的〈Rust is a disappointment〉。這是第二手轉述加評論，不是 Bykozy 的原文，也不是量測報告。轉述的論點包括：

  • 編譯很慢：文中引述 Bykozy 說，因為單型化（monomorphization）與借用檢查，編譯「按設計就很慢」；「十分鐘的建置會殺死心流」。素材沒有附任何編譯時間的測量。
  • 複雜度難以避免：沒有垃圾回收，共享狀態往往要寫成 Arc<Mutex<Box<T>>> 這類形式；圖走訪需要 Rc<RefCell<T>> 之類的變通，傷及易用性與效能。
  • 老手也會跟借用檢查器纏鬥：轉述一位寫了「數十萬行」Rust 的資深開發者，對小改動仍要拆開半個程式碼庫才能過編譯。
  • 可變共享狀態是罩門：GUI、資料庫與有狀態服務會因 Mutex 與 Arc 而損失 Rust 的優勢；快速原型也不實際。
  • 記憶體安全不等於可靠：文中提到一起 Cloudflare 斷線事件被歸因於 unwrap() panic（文章附的是另一個網站的連結，素材未提供細節），重點是 Rust 是「panic」而非未定義行為，仍然會當掉。

同一篇文章也列出支持 Rust 的案例：Discord 語音系統重寫讓每核心 CPU 用量從 20% 降到 5% 以下、訊息儲存從 Go 遷到 Rust 後效能提升 10 倍；Dropbox 儲存後端換成 Rust 後記憶體減少 75%；Linux 核心有超過 15 萬行 Rust；Google 回報 Android 記憶體漏洞減少 70%。這些都是該文章轉述的數字，素材沒有原始出處，本書無法確認，引用時請當作「某報導的說法」。文章的結論是「工具對、炒作錯」：用在核心、嵌入式、剖析器與效能關鍵路徑；不要用在快速原型與有狀態商業邏輯。另外，文中還提到 CPython 核心開發者提議讓 Rust 成為必要依賴，可能讓 Python 在沒有 Rust 支援的平台（文中列出 RISC OS、HP PA-RISC、PowerPC Mac 等）消失，也有互相依賴的 bootstrapping 問題。

Rust 專案自己聽到的挑戰

第二份素材是 Rust Project 成員針對約 70 場訪談（Vision Doc 團隊）整理的〈What we heard about Rust's challenges〉。

🚫
這篇文章已被撤回

文章開頭的作者說明指出：原版文章已被撤回，因為初稿由 LLM 協助撰寫，許多讀者覺得「LLM 腔」讓人不舒服；作者與 Rust 專案其他成員決定整篇撤回。素材保存的是作者之後改以個人評論方式重寫的版本，且他自述會更帶偏見，並承認有些論點因為找不到具體引文而被收斂。所以下列內容只能當作「Rust 專案成員的個人整理」，不是官方研究結論。

作者整理的「所有人都會遇到」的挑戰有四項：

  • 編譯效能：Rust 專案每次合併都追蹤編譯器效能，但永遠還有進步空間。有趣的是，受訪者中沒有人說編譯時間「目前」阻礙他們，只有人擔心程式碼越寫越多後可能出問題。
  • 借用檢查與所有權：幾乎所有初學者都會卡關；但作者說受訪的 Rust 專家已經不太抱怨它，這是會隨經驗消失的挑戰。
  • async：受訪者一致反映有困擾，初學者往往完全略過；作者列出 trait 中的 async fn、async drop、標準 trait 的 async 版本等明確的下一步，但「函式著色」問題還沒有好的解法（呼應第 13 章）。
  • 生態系的 crate：使用者要判斷哪些 crate 可信、哪個最好；某些產業甚至還沒有足夠成熟的 crate。

領域特定的挑戰：嵌入式（資源受限、多數 crate 與標準函式庫難以使用、除錯更難）、安全關鍵系統（最大問題是缺乏可用於認證 Rust 程式碼的成熟工具）、GUI 開發（最大問題是編譯時間，因為視覺變更需要頻繁迭代）。

重寫案例一：Discord，Go 到 Rust

來源是 Discord 官方部落格〈Why Discord is switching from Go to Rust〉（作者 Jesse Howarth；素材的發表日期欄位被截斷為「Feb 27, 20」，文內註記首次移植於 2019 年 5 月完成）。是廠商自述，並非第三方量測。

  • 問題：「Read States」服務（記錄你讀過哪些頻道與訊息，位於熱路徑）用 Go 寫，大多數時候很快，但每隔約 2 分鐘就出現延遲與 CPU 尖峰。
  • 原因：Discord 查 Go 原始碼後發現 Go 最少每 2 分鐘會強制執行一次垃圾回收；而回收需要掃描整個 LRU 快取，才能確認記憶體是否真的沒有參照。調整 GC Percent 沒有效果，因為配置記憶體的速度不足以讓它更常觸發。
  • Go 內的折衷：把 LRU 快取縮小後 GC 尖峰變小，但 99 百分位延遲變高（快取命中率下降、要多讀資料庫）。團隊用大量壓測找到「還可以」的設定。
  • 改用 Rust：該服務小而獨立，且團隊已在其他地方成功用過 Rust。Rust 沒有垃圾回收，快取項目被逐出時立即釋放。重寫時，因為 Rust 型別系統有泛型，可以刪掉 Go 中只因缺乏泛型而存在的程式碼；Rust 的記憶體模型可跨執行緒推理，也能拿掉部分手動跨 goroutine 保護。
  • 結果：壓測顯示 Rust 版延遲與 Go 一樣好、而且沒有延遲尖峰；在基本最佳化之後，在延遲、CPU 與記憶體上全面勝過手工調校過的 Go 版。上線後把快取容量提高到 800 萬筆 Read States，平均時間以微秒計。文中的優化包括：LRU 快取改用 BTreeMap 取代 HashMap 以節省記憶體、換掉初始的度量（metrics）函式庫，改用採現代 Rust 並行寫法的版本、減少記憶體複製。
ℹ️
注意時代背景

文章說當時穩定版 Rust 的 async 還不好用，Discord 選擇使用 nightly 版本並承諾跑到 async 在穩定版完整支援為止，並說「賭贏了」。這與本書第 13 章的 async 已是穩定功能的現況不同。此外文章自己的註腳也說：「我們不認為你應該什麼都用 Rust 重寫」，而且 Rust 的記憶體安全保證有一個例外是 unsafe。

重寫案例二：Cloudflare Pingora

數字與動機已在上一章詳述（CPU 約少 70%、記憶體約少 67%、連線重用率從 87.1% 到 99.92%）。這裡只強調閱讀方式：它是 Cloudflare 自己的說法；而且文章明確說明延遲改善（TTFB 中位數少 5 毫秒）「不是因為程式跑得更快」，是來自架構改變（跨執行緒共享連線池）。換句話說，這個案例是「架構加語言」一起換，無法把成果全部算在 Rust 頭上。

重寫案例三：Momento，Kotlin 到 Rust

來源是 InfoQ 上 Ramya Krishnamoorthy 在 QCon 的演講〈Myth Busters: is Rust a Slam Dunk?〉（2025-09-18 發布），她是 Momento（早期新創，提供無伺服器快取與訊息匯流排等服務）的工程主管。這份素材的價值在於它同時列出了好處與代價，講者的結論是「有條件的是」。

背景與動機

  • 起初用 Kotlin 上線，團隊多半有 JVM 背景。20K TPS 的簡單 get/set 負載，單節點基準是 p999 約 4.99 毫秒。
  • 加入需要新儲存引擎的新資料型別後，第一版（儲存抽象層用 Rust、路由層仍是 Kotlin）在相同負載下 p999 從 5 毫秒退步到 9.3 毫秒。
  • 瓶頸包括 GC 造成不可預測的尖峰、Kotlin 在 Graviton（Amazon 的 ARM）上較慢、Netty 問題；團隊嘗試調整執行緒數、加第二個 epoll 迴圈、調整 G1 垃圾回收器，後來收益只剩邊際遞減。
  • 講者的目標是「可預測的低尾端延遲」與「成本效率」；她也說 Graviton 最多能省約 40% 成本。

採用的方式與風險

決定改寫路由服務後，團隊採漸進式遷移：先用 Rust 寫新的 Topics 服務，再逐一把快取 API 搬過去，新功能一律 Rust 優先；用 Rust 與 Kotlin 路由服務並行，依功能分流，縮小爆炸半徑。講者明說的風險：

  • 花好幾個開發月重寫，而不是做新功能，對早期新創是大風險。
  • 初期無法功能對等，需同時運行兩套系統，增加維運負擔。
  • Rust 生態不穩定：她提到 tonic 等熱門 crate 仍是不穩定版本，hyper 升到 1.0 時有破壞性變更，需重寫 TCP accept loop；有一次升級 tonic 的次要版本，改變了 TLS 伺服器對 I/O 錯誤的處理方式（改成視為致命錯誤），導致正式環境服務被關閉。

培養內部能力的做法：先把維運工具改成 Rust（練習而不會弄掛服務）、建立可複製的程式碼模板、分享文化與用程式碼審查當教學。

效能的「不受歡迎的真相」

講者說：你也可以用 Rust 寫出慢程式。在 Kotlin 下單節點撐不過 20K TPS，改用 Rust 達到 32K TPS，但此時尾端延遲會突然從 5 毫秒以下飆到 100 毫秒。她們用 Tokio 的任務排程指標與火焰圖，找到 h2 crate 內同步 mutex 的競爭（講者說相關議題自 2021 年起就開著）：路由服務與儲存服務之間為了少建連線，只用少數持久的 gRPC channel，於是每條 HTTP/2 連線上有許多 stream，Tokio 多執行緒 runtime 又會讓同一條連線的 RPC 被不同 worker 執行緒搶同一把鎖，等鎖的執行緒什麼都不能做。解法依序是：

  1. 換不同的鎖實作：有改善，但 h2 位於堆疊底層，修補它會陷入依賴地獄，所以沒採用。
  2. 把路由到儲存的通訊分到另一個 runtime：單節點吞吐量從 32K 提高到 40K TPS，p99 維持在 10 毫秒以下，但在 runtime 之外產生 task 的排程成本較高。
  3. 內部通訊拿掉 tonic 與 hyper，自建 protosockets（在原始 TCP 連線上交換 Protobuf 訊息）繞過 h2：單一 c7g.2xlarge 達到 65K TPS，p999 仍低於 10 毫秒。

講者還提醒，只把 Amazon Linux 2 升級到 Amazon Linux 2023，就從 65K 到 75K TPS，p999 降到約 7.5 毫秒；選對執行個體類型也能有大幅改善。換句話說，不要忽略更簡單的做法。

回頭看，會再做一次嗎？

講者的答案是「有條件的是」：延遲保證、通過客戶自己的壓測、以低成本推出新功能是好處；功能開發速度受影響是真實的商業風險、生態系不穩定曾引發停機、底層 crate 出問題時繞過去的成本很高是代價。問答中有人問開發者生產力是否跟 Kotlin 一樣好，她說一年後因為有了固定模式而提升，但沒有量測，且承認在 Kotlin 建立同樣模式也「可能」有相同提升；她個人覺得最難的是編譯時間，以及遇到困難時會被誘惑去用 unsafe 繞過（她是拿 C++ 比較，而非 Kotlin）。

小結

三個重寫案例有共同點：問題都有明確可量測的瓶頸（GC 尖峰、連線池不能共享），而且選的元件都夠小或能漸進替換。批評也並非空穴來風：編譯時間、借用檢查的學習曲線、async 的粗糙、生態系的不穩定，在不同素材裡都以不同形式出現，連 Rust 專案成員的整理也承認。比較務實的態度，是把 Rust 當成在「記憶體安全、可預測延遲與長期維護」上特別強、但要付學習與生態成本的工具，而不是萬靈丹。
