第 6 章 · Part 2：所有權：Rust 的核心

借用與參考：有契約的共享

不想把資料「過戶」給別人，只想借他看或改一下：參考與借用規則。

上一章結尾留下一個痛點：函式想用一個 String，卻得先把所有權拿走再還回來，連 tuple 都搬出來了。解法是參考（reference）：拿到資料的位址，但不拿走所有權。

ℹ️
本章素材來源

主要範例與編譯器輸出取自官方 The Rust Programming Language 的 References and Borrowing；迴圈借用的案例取自 ZetCode 的 Rust ownership and borrowing（個人教學站，非官方）；Go 與 data race 的對比取自 iT 邦幫忙 2025 鐵人賽〈(Day3) Rust 借用 (Borrowing)：有契約的共享〉。

參考：指向資料，但不擁有它

官方文件這樣描述：參考像指標，是一個可以順著走到資料的位址，而那份資料屬於別的變數所有。與指標不同的是，參考保證在它的整個存續期間，都會指向某個特定型別的有效值。

用參考當參數，不取得所有權（官方 Rust Book）
fn main() {
    let s1 = String::from("hello");

    let len = calculate_length(&s1);

    println!("The length of '{s1}' is {len}.");
}

fn calculate_length(s: &String) -> usize { // s is a reference to a String
    s.len()
} // Here, s goes out of scope. But because s does not have ownership of what
  // it refers to, the String is not dropped.

呼叫端寫 &s1，函式簽名寫 &String。這個 & 讓你引用某個值而不取得所有權。因為 s 不擁有它指向的 String，函式結束時 String 不會被 drop，也就不必把值還回去，因為根本沒拿走。官方文件把建立參考的動作稱為借用（borrowing）：像現實生活一樣，借來的東西用完要還，而且它不是你的。

與 & 相反的動作是解參考（dereference），運算子是 *；官方文件說會在後面章節（Chapter 8、15）再討論，本書留到智慧指標那一章。

預設不可修改，要改得用 &mut

就像變數預設不可變，參考也是。拿到 &String 就不能修改它：

Listing 4-6：嘗試修改借來的值（官方 Rust Book，無法編譯）
fn main() {
    let s = String::from("hello");

    change(&s);
}

fn change(some_string: &String) {
    some_string.push_str(", world");
}
編譯器輸出（官方 Rust Book）
$ cargo run
   Compiling ownership v0.1.0 (file:///projects/ownership)
error[E0596]: cannot borrow `*some_string` as mutable, as it is behind a `&` reference
 --> src/main.rs:8:5
  |
8 |     some_string.push_str(", world");
  |     ^^^^^^^^^^^ `some_string` is a `&` reference, so it cannot be borrowed as mutable
  |
help: consider changing this to be a mutable reference
  |
7 | fn change(some_string: &mut String) {
  |                         +++

For more information about this error, try `rustc --explain E0596`.
error: could not compile `ownership` (bin "ownership") due to 1 previous error

錯誤訊息的 help 已經告訴你答案：改用可變參考。做法有三處：變數要宣告 mut、呼叫端寫 &mut s、函式簽名寫 &mut String。這也讓「這個函式會修改它借到的值」在簽名上一目了然。

可變參考（官方 Rust Book）
fn main() {
    let mut s = String::from("hello");

    change(&mut s);
}

fn change(some_string: &mut String) {
    some_string.push_str(", world");
}

借用的契約：一寫或多讀

可變參考有個很大的限制：只要存在某個值的可變參考，就不能有任何其他參考指向它。同時建立兩個就無法編譯：

兩個可變參考（官方 Rust Book，無法編譯）
fn main() {
    let mut s = String::from("hello");

    let r1 = &mut s;
    let r2 = &mut s;

    println!("{r1}, {r2}");
}
編譯器輸出（官方 Rust Book）
$ cargo run
   Compiling ownership v0.1.0 (file:///projects/ownership)
error[E0499]: cannot borrow `s` as mutable more than once at a time
 --> src/main.rs:5:14
  |
4 |     let r1 = &mut s;
  |              ------ first mutable borrow occurs here
5 |     let r2 = &mut s;
  |              ^^^^^^ second mutable borrow occurs here
6 |
7 |     println!("{r1}, {r2}");
  |                -- first borrow later used here

For more information about this error, try `rustc --explain E0499`.
error: could not compile `ownership` (bin "ownership") due to 1 previous error

iT 邦幫忙那篇文章把這條規則濃縮成一句：要嘛很多人一起讀（&T），要嘛只有一個人能寫（&mut T）。官方文件說明這條限制的好處：Rust 能在編譯期就防止 data race。data race 發生在同時滿足三個條件時：

  • 兩個以上的指標同時存取同一份資料；
  • 至少有一個指標用來寫入；
  • 沒有任何同步存取的機制。

data race 會造成未定義行為，執行期很難追查；Rust 的做法是乾脆不讓這種程式碼通過編譯。需要多個可變參考時，可以用大括號分出新作用域，只要不是「同時」存在即可：

用作用域錯開可變參考（官方 Rust Book）
fn main() {
    let mut s = String::from("hello");

    {
        let r1 = &mut s;
    } // r1 goes out of scope here, so we can make a new reference with no problems.

    let r2 = &mut s;
}

可變與不可變參考混用，也適用類似的規則：

同時持有不可變與可變參考（官方 Rust Book，無法編譯）
fn main() {
    let mut s = String::from("hello");

    let r1 = &s; // no problem
    let r2 = &s; // no problem
    let r3 = &mut s; // BIG PROBLEM

    println!("{r1}, {r2}, and {r3}");
}
編譯器輸出（官方 Rust Book）
$ cargo run
   Compiling ownership v0.1.0 (file:///projects/ownership)
error[E0502]: cannot borrow `s` as mutable because it is also borrowed as immutable
 --> src/main.rs:6:14
  |
4 |     let r1 = &s; // no problem
  |              -- immutable borrow occurs here
5 |     let r2 = &s; // no problem
6 |     let r3 = &mut s; // BIG PROBLEM
  |              ^^^^^^ mutable borrow occurs here
7 |
8 |     println!("{r1}, {r2}, and {r3}");
  |                -- immutable borrow later used here

For more information about this error, try `rustc --explain E0502`.
error: could not compile `ownership` (bin "ownership") due to 1 previous error

原因很直覺：正在讀的人不會預期資料突然被改掉；多個不可變參考則沒問題，因為只讀的人不會影響別人。

參考的範圍到「最後一次使用」為止

官方文件特別提醒：參考的作用範圍從它被建立開始，持續到最後一次被使用為止。所以下面的程式可以編譯：r1 與 r2 最後一次使用在第一個 println!，之後才建立 r3，兩段範圍沒有重疊。

不可變參考用完之後才建立可變參考（官方 Rust Book）
fn main() {
    let mut s = String::from("hello");

    let r1 = &s; // no problem
    let r2 = &s; // no problem
    println!("{r1} and {r2}");
    // Variables r1 and r2 will not be used after this point.

    let r3 = &mut s; // no problem
    println!("{r3}");
}

ZetCode 的文章把這個機制稱為 non-lexical lifetimes（NLL，非詞法生命週期）：編譯器看出 r1 與 r2 在第一個 println! 之後不再使用，所以後面的可變借用有效；如果在建立 r3 之後還用 r1，就會被拒絕。這個名詞出自非官方來源，官方 Rust Book 這一節只描述了行為。

懸空參考：編譯器保證不存在

在有指標的語言裡，很容易不小心造出懸空指標（dangling pointer）：記憶體已經釋放並可能給了別人，指標卻還留著。Rust 的保證是：如果你持有某資料的參考，編譯器會確保資料不會比參考更早離開作用域。

試圖回傳區域變數的參考（官方 Rust Book，無法編譯）
fn main() {
    let reference_to_nothing = dangle();
}

fn dangle() -> &String { // dangle returns a reference to a String

    let s = String::from("hello"); // s is a new String

    &s // we return a reference to the String, s
} // Here, s goes out of scope and is dropped, so its memory goes away.
  // Danger!
編譯器輸出（官方 Rust Book）
$ cargo run
   Compiling ownership v0.1.0 (file:///projects/ownership)
error[E0106]: missing lifetime specifier
 --> src/main.rs:5:16
  |
5 | fn dangle() -> &String {
  |                ^ expected named lifetime parameter
  |
  = help: this function's return type contains a borrowed value, but there is no value for it to be borrowed from
help: consider using the `'static` lifetime, but this is uncommon unless you're returning a borrowed value from a `const` or a `static`
  |
5 | fn dangle() -> &'static String {
  |                 +++++++
help: instead, you are more likely to want to return an owned value
  |
5 - fn dangle() -> &String {
5 + fn dangle() -> String {
  |

For more information about this error, try `rustc --explain E0106`.
error: could not compile `ownership` (bin "ownership") due to 1 previous error

錯誤訊息提到「missing lifetime specifier」，那是下一章的主題；暫時忽略生命週期的部分，關鍵是這一句：函式的回傳型別含有借用的值，但沒有任何值可供借用。s 在 dangle 內建立，函式一結束就被釋放，回傳指向它的參考就會指向無效的 String。編譯器的建議之一是直接回傳擁有所有權的值：

改成直接回傳 String（官方 Rust Book）
fn main() {
    let string = no_dangle();
}

fn no_dangle() -> String {
    let s = String::from("hello");

    s
}

參考的兩條規則

💡
The Rules of References（官方 Rust Book）

任一時間點，你可以擁有「一個可變參考」或「任意多個不可變參考」，兩者擇一；而參考必須永遠有效。

實戰：迴圈裡常見的借用錯誤

ZetCode 的文章指出一個新手常踩的坑：一邊走訪集合、一邊修改它。s.chars() 會回傳一個持有 s 不可變借用的迭代器，這個借用在整個迴圈期間都有效；迴圈內呼叫 s.push(c) 需要可變借用，於是被拒絕（錯誤碼同為 E0502）。

迴圈中修改正在走訪的字串（ZetCode，無法編譯）
// This code does NOT compile — shown for illustration only.

fn main() {
    let mut s = String::from("abc");
    for c in s.chars() {
        s.push(c); // ERROR: cannot borrow `s` as mutable
                // because it is also borrowed as immutable
    }
    println!("{}", s);
}

修法依需求而定。想把每個字元重複兩次，可以把結果寫進另一個新字串；只想過濾字元，可以用 retain；對 Vec 則可以用索引，每次迭代都建立新的借用，而不是整個迴圈持有同一個。

修法一：寫入新的 String（ZetCode）
fn main() {
    let s = String::from("abc");
    let mut result = String::new();

    for c in s.chars() {
        result.push(c);
        result.push(c);
    }

    println!("{}", result);
}
修法二：用 retain 過濾（ZetCode）
fn main() {
    let mut s = String::from("a1b2c3");
    s.retain(|c| c.is_alphabetic());
    println!("{}", s);
}
修法三：用索引走訪 Vec（ZetCode）
fn main() {
    let mut v = vec![1, 2, 3, 4];
    for i in 0..v.len() {
        v[i] *= 2; // fine: no iterator borrow
    }
    println!("{:?}", v);
}

ZetCode 補充了索引的限制：對 Vec 用索引沒問題，但 String 是 UTF-8 編碼，用位元組位置索引很脆弱，需要字元層級操作時改用 char_indices() 或收集成 Vec<char>。

為什麼要這麼嚴？與其他語言對照

iT 邦幫忙的文章用 Python／JavaScript 與 Go 做對照：在 Python 或 JavaScript 裡，共享是隱式的，你不知道有多少參考指向同一份資料，也不知道誰會在何時修改它；Go 透過指標讓共享變得顯式，但文章指出 Go 無法在編譯期阻止 data race。Rust 把共享變成「有契約的」：&T 表示只想讀、&mut T 表示要獨佔寫入、T 表示要取得所有權。

⚠️
素材的限制

stub 原先預告的 RefCell、Mutex 與內部可變性，本章素材並未提供，因此不在此展開；它們屬於「把借用檢查延到執行期」的工具，留待智慧指標與並行章節。

💡
本章重點回顧

& 借用不拿走所有權；&mut 需要 mut 變數且同時只能存在一個；可變與不可變參考不能重疊；參考的範圍到最後一次使用為止；參考永遠不會懸空。
