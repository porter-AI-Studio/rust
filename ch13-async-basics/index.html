第 13 章 · Part 4：並行與非同步

async/await 基礎

理解 Future 如何由 runtime 推進，並掌握 await、併發組合與避免阻塞的基本原則。

上一章用執行緒處理並行；這一章換另一條路：async／await。它解決的是同一類問題，但成本結構不同，兩者在多數情況下是互補而非取代（官方 Rust Book 第 17 章的說法）。

為什麼需要 async：I/O-bound 與阻塞

官方 Rust Book 第 17 章用兩個例子區分工作類型：匯出影片是 CPU-bound（受限於 CPU／GPU 的運算速度），下載影片是 I/O-bound（受限於網路與磁碟的輸入輸出速度）。作業系統的許多網路 API 是 blocking：資料沒有完全就緒之前，程式就卡在那裡。為每個下載都開一條執行緒可以避免卡住主執行緒，但執行緒佔用的系統資源最終會成為問題；官方書的結論是，更理想的做法是呼叫本身不阻塞，讓 runtime 自行決定執行順序。

《Asynchronous Programming in Rust》（async-book）進一步說明：用 async，並發發生在你的程式內部，task 的切換與排程由 async runtime 管理，而不是由作業系統替每個 task 建立執行緒（網路與檔案 I/O 本身仍透過作業系統提供的機制完成，這句是本書補充），由 async runtime（Rust 裡只是另一個 crate）搭配程式設計師明確用 await 讓出控制權來管理 task；因此情境切換很快、每個 task 的記憶體負擔遠小於作業系統執行緒，適合要處理大量並發、且多半在等待的系統，也適合沒有作業系統執行緒可用的微控制器。

並發與平行

官方書把兩者分開：一個人同時握著多個任務、在它們之間切換，是並發（concurrency）；多人各做一件事、同時前進，是平行（parallelism）；有依賴關係的部分仍是序列。在 Rust 裡跑 async 程式通常是並發，視硬體、作業系統與 runtime 而定，底層也可能用到平行。

ℹ️
async 不是萬靈丹

第三方文章（Reintech，2026-02）列出適用時機：I/O 為主、需要高並發、網路服務、資料庫連線池適合 async；純 CPU 運算、簡單腳本或 CLI 工具、無法避免阻塞操作的情況則不建議。這是單一作者的經驗整理，不是官方結論。

第一個 async 函式

先看 async-book 的 hello world。async fn 定義非同步函式，用 .await 呼叫；async-book 特別提醒，Rust 的 async 函式不被 await 就什麼都不做。（該書也在註腳承認，println 其實是阻塞 I/O，這只是一個示意範例。）

async-book 的 hello world
// Define an async function.
async fn say_hello() {
    println!("hello, world!");
}

#[tokio::main] // Boilerplate which lets us write `async fn main`, we'll explain it later.
async fn main() {
    // Call an async function and await its result.
    say_hello().await;
}

官方 Rust Book 以 trpl crate（The Rust Programming Language 的縮寫，內部主要重新匯出 futures 與 tokio 的內容）寫了一個小爬蟲。第一步是取得網頁 <title> 的函式：

官方 Rust Book Listing 17-1
use trpl::Html;

async fn page_title(url: &str) -> Option<String> {
    let response = trpl::get(url).await;
    let response_text = response.text().await;
    Html::parse(&response_text)
        .select_first("title")
        .map(|title| title.inner_html())
}

兩個 await 都不能省，因為 Rust 的 future 是惰性的（lazy）：你不要求它，它就不動，不使用 future 時編譯器還會警告。這和上一章 thread::spawn 一建立就開始跑的行為不同，也呼應迭代器不呼叫 next 就什麼都不做。另外，Rust 的 await 是後置關鍵字，寫成 trpl::get(url).await.text().await 可以讓鏈式呼叫更好讀。

async 其實是 Future 的語法糖

官方書說明：編譯器把標了 async 的區塊編成一個獨一無二、實作 Future trait 的匿名型別；async fn 則編成一個一般函式，函式本體是 async 區塊，回傳型別就是那個匿名型別。因此 Listing 17-1 大致等價於：

官方 Rust Book：async fn 的等價寫法
use std::future::Future;
use trpl::Html;

fn page_title(url: &str) -> impl Future<Output = Option<String>> {
    async move {
        let text = trpl::get(url).await.text().await;
        Html::parse(&text)
            .select_first("title")
            .map(|title| title.inner_html())
    }
}

每個 await 點都是把控制權交還給 runtime 的地方。為了讓 runtime 之後能回來接續，Rust 需要保存區塊的狀態：就好像你手寫了一個 enum，在每個 await 點記錄目前進度。實際上這個狀態機由編譯器自動產生，所有權與借用規則照常適用。

官方書的概念示意（編譯器實際產生的狀態機）
enum PageTitleFuture<'a> {
    Initial { url: &'a str },
    GetAwaitPoint { url: &'a str },
    TextAwaitPoint { response: trpl::Response },
}

Future trait：poll、Pin 與 Waker

下面是標準函式庫文件（doc.rust-lang.org/std/future/trait.Future.html）裡的 trait 定義。官方文件對 poll 的描述是：嘗試把 future 解析成最終值，若值尚未就緒，則登記目前的 task 以便之後喚醒。

std::future::Future（官方文件）
pub trait Future {
    type Output;

    // Required method
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}
  • Poll::Pending：future 還沒好；Poll::Ready(val)：已完成並帶出結果。官方文件註明，future 完成之後不應再被 poll。
  • Context 可以提供 Waker，它是用來喚醒目前 task 的把手。future 回傳 Pending 時，會保存從 Context 複製出來的 Waker，等到能繼續推進時再喚醒；多次 poll 時，只有最近一次傳入的 Waker 需要被排程喚醒。
  • Pin<&mut Self> 在 trait 簽章中出現。本章素材與該頁文件都只列出簽章、未解釋 Pin 的用途；進一步的細節素材未提供，需查 std::pin 文件。

為什麼 main 不能是 async：執行器

把 main 標成 async 會得到 E0752 錯誤（main function is not allowed to be async）。原因是 async 程式碼需要 runtime 來管理執行細節，而 main 是程式的起點，它可以初始化 runtime，但自己不是 runtime。多數語言把 runtime 綁在語言裡；Rust 不內建，而是交給 crate 選擇，因為高吞吐量網路伺服器與只有單核心、小 RAM、沒有堆積配置的微控制器，需求完全不同。執行狀態機的那一部分稱為 executor（執行器）。

下例用 trpl::block_on，它會阻塞目前執行緒直到 future 完成，並在背後用 tokio 建立 runtime：

官方 Rust Book Listing 17-4
use trpl::Html;

fn main() {
    let args: Vec<String> = std::env::args().collect();

    trpl::block_on(async {
        let url = &args[1];
        match page_title(url).await {
            Some(title) => println!("The title for {url} was {title}"),
            None => println!("{url} had no title"),
        }
    })
}

async fn page_title(url: &str) -> Option<String> {
    let response_text = trpl::get(url).await.text().await;
    Html::parse(&response_text)
        .select_first("title")
        .map(|title| title.inner_html())
}

部分 runtime 提供巨集讓你寫 async main（例如開頭的 #[tokio::main]），那些巨集會把它改寫成一般的 fn main，做的事和上面手寫的一樣。

併發：select 與 join

兩個 future 賽跑，看哪個先完成，用 trpl::select；它回傳 Either（有 Left 與 Right，沒有成功或失敗的語意）：

官方 Rust Book Listing 17-5
use trpl::{Either, Html};

fn main() {
    let args: Vec<String> = std::env::args().collect();

    trpl::block_on(async {
        let title_fut_1 = page_title(&args[1]);
        let title_fut_2 = page_title(&args[2]);

        let (url, maybe_title) =
            match trpl::select(title_fut_1, title_fut_2).await {
                Either::Left(left) => left,
                Either::Right(right) => right,
            };

        println!("{url} returned first");
        match maybe_title {
            Some(title) => println!("Its page title was: '{title}'"),
            None => println!("It had no title."),
        }
    })
}

async fn page_title(url: &str) -> (&str, Option<String>) {
    let response_text = trpl::get(url).await.text().await;
    let title = Html::parse(&response_text)
        .select_first("title")
        .map(|title| title.inner_html());
    (url, title)
}

若要「全部完成才繼續」，Reintech 的文章示範用 tokio::join!。該文宣稱 5 個各需 100 毫秒的呼叫，依序要 500 毫秒、join! 下約 100 毫秒（作者的說明，非實測數據）。注意文中把這稱為「平行」，嚴格說 join! 是在同一個 task 內並發地推進多個 future。

Reintech 文章範例（片段，未附 fetch_from_api）
use tokio;

async fn fetch_and_process_concurrent() -> String {
    // Start both operations at once
    let task1 = fetch_from_api("https://api.example.com/data1");
    let task2 = fetch_from_api("https://api.example.com/data2");

    // Wait for both to complete
    let (data1, data2) = tokio::join!(task1, task2);

    format!("{} + {}", data1, data2)
}

不要阻塞 runtime

Reintech 文章指出，async 程式碼最大的錯誤是呼叫阻塞操作：std::thread::sleep 或同步的資料庫查詢會卡住整條執行緒，使其他 task 無法執行。必須做阻塞工作時，改用 tokio::task::spawn_blocking。

Reintech 文章範例（片段）
// WRONG - blocks the executor thread
async fn bad_example() {
    std::thread::sleep(Duration::from_secs(1)); // Don't do this!
}

// CORRECT - yields to other tasks
async fn good_example() {
    tokio::time::sleep(Duration::from_secs(1)).await; // Do this instead
}
Reintech 文章範例（片段）
async fn handle_blocking_work() -> Result<Data, Error> {
    tokio::task::spawn_blocking(|| {
        // Expensive CPU work or blocking I/O
        heavy_computation()
    }).await?
}
⚠️
目前的粗糙之處

async-book 自己承認：async Rust 在穩定版編譯器與標準函式庫提供的部分是可靠且有效率的，已用在大型科技公司的嚴苛場景，但仍有不完整之處。使用者最常遇到的粗糙處是 async iterator（stream），部分 trait 中的 async 用法支援不佳，也沒有好的非同步解構（async destruction）解法。

Stream 與其他主題

官方書把 stream（非同步的序列，類似非同步版的迭代器）列為 async 三大元件之一，Reintech 文章也示範用 StreamExt 的 next().await 迴圈取值。本章素材沒有逐步講解 Stream 的 trait 細節、非同步 trait 與取消安全（cancel safety），這些主題素材未提供，這裡不展開，以免寫成推測。

小結與下一章

重點整理：future 是惰性的，async 編成實作 Future 的狀態機，await 是讓出控制權的點，而執行這一切的是 runtime 中的 executor；Rust 刻意不內建 runtime。下一章要進入實務上最常用的 runtime：Tokio，並用 axum 寫出一個非同步 Web 服務。
