系統層：Rust for Linux、嵌入式與 Pingora

系統層：Rust for Linux、嵌入式與 Pingora

Rust 的出身就是系統程式語言。這一章看它在三個系統層場景的實際狀況：Linux 核心、嵌入式裝置，以及 Cloudflare 自行打造的代理伺服器 Pingora。所有數字與說法都標明來源，並且保留各自的立場。

Rust for Linux

依 Rust Project Goals 文件（rust-lang 專案目標，官方），Rust 現在已是 Linux 核心不可或缺的一部分：核心主線已有以 Rust 寫成的驅動與工具，甚至有直接在核心裡的功能（文件舉的例子是 DRM panic 的 QR code 產生器）。Rust for Linux 專案主導開發，Rust 專案負責協助協調，雙方每兩週開一次例會，語言與編譯器團隊都有代表參加。

目前的限制與目標

文件坦承：核心雖然用穩定版 Rust 編譯器建置，卻依賴許多不穩定的語言功能（透過 #![feature(...)] 宣告），而且目前受限於 LLVM 支援的平台。最終目標是：只用穩定版 Rust（不需任何 feature gate）建置核心 release，並支援 Linux 本身支援的所有目標平台。「完成」的定義也很明確：所有列出的工作都進入穩定版 Rust，建置核心不再需要 #![feature(...)]。

2026 年的目標清單包括（時間以文件標示為準）：

項目時程用途（依文件）
Arbitrary self types2026讓使用者自訂的智慧指標可當方法接收者
derive(CoercePointee)2026讓自訂智慧指標支援 dyn Trait 轉換
build-std2026讓 Cargo 針對自訂目標從原始碼重建標準函式庫
const traits MVP2026讓 const fn 可呼叫 trait 方法

Guaranteed destructors2026-2027探索讓型別可以選擇不被 mem::forget
In-place initialization2026-2028直接在最終位置建立值，不經過搬移

文件的經費表顯示 build-std 有 Arm 贊助、費用待定；完整 const generics 則標示為「需要資金」、聯絡對象是 Hexcat。文件另列出其他關注主題但無專案目標，例如 rustfmt 的「kernel vertical style」、coherence domains、niche optimizations、安全的 transmutation 等。

ℹ️
為什麼核心要 Rust

文件在動機中說，除了語言功能穩定化，Rust for Linux 還展示了 Rust 在系統軟體的更廣泛價值：把 unsafe 程式碼隔離以減少嚴重錯誤、提升整個核心的程式碼品質（連 C 端的 API 也變得更清楚、文件更完整），並吸引原本不敢寫底層 C 的新貢獻者。這是專案方的自述，不是第三方評估。

寫核心模組的門檻：環境準備

依 Linux 核心官方文件 Quick Start，需要的工具包括：rustc（新版編譯器）、Rust 標準函式庫原始碼（因為建置系統會交叉編譯 core）、libclang（bindgen 用它理解核心的 C 程式碼）、以及在建置時產生 C 端綁定的 bindgen。開發時另外需要 rustfmt、clippy、rustdoc，還可用 rust-analyzer。

最簡單的方式是用發行版套件，文件舉了 Arch、Debian、Fedora、Gentoo、Nix、openSUSE、Ubuntu 的作法（節錄三種）：

Linux 核心文件：發行版安裝範例（節錄）
# Debian
apt install rustc rust-src bindgen rustfmt rust-clippy

# Fedora
dnf install rust rust-src bindgen-cli rustfmt clippy

# Arch Linux
pacman -S rust rust-src rust-bindgen

也可用 rustup 安裝工具鏈（文件說明 rust-src 元件是依工具鏈安裝，之後升級編譯器要重新加入）：

Linux 核心文件：rustup 與 bindgen（節錄）
rustup override set stable
rustup component add rust-src
cargo install --locked bindgen-cli

檢查需求是否滿足、以及建置核心，文件的說法是：用完整 LLVM 工具鏈建置是目前支援最好的設定；用 GCC 在部分設定下也能運作，但目前非常實驗性。

Linux 核心文件：檢查與建置
make LLVM=1 rustavailable
make LLVM=1

在設定選單中，要先啟用 Rust support（CONFIG_RUST），然後到下列路徑啟用 Rust 範例模組，範例原始碼在 samples/rust/：

Linux 核心文件：啟用 Rust 範例

    -> Sample kernel code
        -> Rust samples

嵌入式

Rust 官方嵌入式頁面（rust-lang.org，官方行銷性質）列出六個賣點：

  • 靜態分析：在編譯期強制檢查腳位與周邊設定，保證資源不會被應用程式的非預期部分使用。
  • 彈性記憶體：動態記憶體配置是可選的，可用全域配置器與動態資料結構，也可以完全不用堆積、全部靜態配置。
  • 無畏並行：不會意外在執行緒之間共享狀態。
  • 互通性：可整合進既有的 C 程式碼庫，或利用既有 SDK 寫 Rust 應用。
  • 可攜性：函式庫或驅動寫一次，可用在從極小微控制器到強大單板電腦的各種系統。
  • 社群驅動。

頁面引用了若干公司的使用心得（例如 Sensirion 用 Rust 做粒狀物感測器的嵌入式展示、Airborne Engineering 用 Rust 寫乙太網路 bootloader blethrs），這些都是廠商自述的正面見證，頁面沒有提供效能或成本數據。另外，async-book 提過微控制器沒有作業系統執行緒時，async 是適合的選擇（見第 13 章）。

⚠️
素材未涵蓋

大綱預告的 no_std／alloc 的技術細節、裝置驅動模式、靜態連結、二進位大小優化與交叉編譯工具鏈，本章素材沒有逐項說明，這裡不展開。嵌入式頁面只提到「動態配置為可選」；實務請參閱 Rust Embedded Book（docs.rust-embedded.org/book）。

Pingora：Cloudflare 的 Rust 代理

以下全部來自 Cloudflare 自己的工程部落格〈How we built Pingora〉，是廠商第一手說明，數字沒有第三方驗證；素材未標註發表日期。

為什麼要重寫

Cloudflare 說，規模成長後 NGINX 已不敷使用，主要原因有三：

  • 架構限制：每個請求只能由單一 worker 處理，造成 CPU 核心負載不均；而且連線池是每個 worker 各自一份，增加 worker 數反而讓連線重用率變差，TTFB 變慢、需維護的連線更多。
  • 難以加功能：例如重試或容錯時要送到不同來源、帶不同標頭，NGINX 不允許；NGINX 是純 C（非記憶體安全），輔助的 Lua 較不危險但較慢且缺少靜態型別。
  • 社群因素：作者認為 NGINX 社群不活躍、開發偏向「閉門造車」。

他們評估過三條路：繼續投資 NGINX 甚至 fork、改用其他第三方代理（如 Envoy）、或從零自建。文章說每季都重新評估，沒有明確公式，最終因自建的投資報酬率看起來值得而決定自建。

設計決策

  • 語言選 Rust：能做 C 能做的事，又有記憶體安全而不犧牲效能。
  • 自建 HTTP 函式庫：因為要支援大量非 RFC 規範的流量。文章舉例：RFC 9110 的狀態碼是三位數整數、一般預期在 100 至 599，但許多伺服器用 599 到 999 的狀態碼；hyper 後來接受了這項修改，但這只是眾多不合規行為之一。
  • 多執行緒加 work stealing：選多執行緒而非多行程，方便共享資源（尤其連線池）；Tokio 非同步 runtime 被認為很適合（與第 14 章呼應）。
  • 「請求生命週期」事件式可程式介面：類似 NGINX／OpenResty，例如「request filter」階段可修改或拒絕請求，以便把業務邏輯和通用代理邏輯分開。

生產環境的結果（Cloudflare 自述）

面向文章中的說法
規模每天處理超過 1 兆個請求
延遲整體 TTFB 中位數少 5 毫秒、第 95 百分位少 80 毫秒；文章說這不是因為程式跑得更快，而是跨執行緒共享連線帶來更好的連線重用
連線新連線數只有舊服務的三分之一；一個大客戶的連線重用率從 87.1% 升到 99.92%，對來源站的新連線減少 160 倍
資源相同流量下 CPU 約少 70%、記憶體約少 67%（開場另說只需先前的三分之一 CPU 與記憶體）
穩定性自推出以來處理了數百兆個請求，尚未因服務程式碼崩潰
功能較容易加入 HTTP/2 upstream，之後提供 gRPC；Cache Reserve 以 R2 當快取層

節省的來源，文章歸納為：Rust 程式比舊的 Lua 程式有效率；Pingora 直接存取標頭字串，而 NGINX／Lua 要讀 C 結構、配置 Lua 字串再複製並由 GC 回收；多執行緒模型可透過原子參照計數（Arc）直接共享資料，而 NGINX 共享記憶體每次存取都要用 mutex 且只能放字串與數字；加上減少新連線所省下的 TLS 握手成本。

⚠️
這是重寫案例，不是單純「換語言」的對照

Cloudflare 同時改了架構（行程模型改成多執行緒共享連線池）與語言（C／Lua 改成 Rust）。文章也承認效益來自兩者加總，所以不能把全部功勞歸給 Rust；下一章會再回頭討論這點。

小結與下一章

Linux 核心的 Rust 還在邊用邊爭取語言功能穩定化的階段；嵌入式有彈性的記憶體模型與編譯期檢查，但素材多半是官方與廠商的自我描述；Pingora 提供了一個有數字的大規模案例。這些都偏正面，下一章換個角度：看批評者怎麼說、Rust 的代價在哪裡，以及重寫案例該怎麼解讀。
