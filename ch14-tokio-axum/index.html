第 14 章 · Part 4：並行與非同步

用 Tokio 與 axum 寫非同步程式

以 Tokio 驅動非同步工作，搭配 axum 處理 HTTP 請求，並用 Serde 在 Rust 型別與 JSON 間轉換。

上一章說過，Rust 不內建 runtime，必須由 crate 提供。本章用最常見的組合：Tokio（runtime）加 axum（HTTP 路由與請求處理），再搭配 Serde 做資料序列化。

Tokio：從 Hello Tokio 開始

依 Tokio 官方教學（tokio.rs/tokio/tutorial/hello-tokio），Tokio 是用來寫可靠非同步應用的 runtime，提供非同步 I/O、網路、排程、計時器等。教學的第一個程式會連上 Mini-Redis 伺服器，把鍵 hello 設成 world，再讀回來。

建立專案（官方教學）
$ cargo new my-redis
$ cd my-redis

在 Cargo.toml 的 [dependencies] 下加入：

Cargo.toml（官方教學）
tokio = { version = "1", features = ["full"] }
mini-redis = "0.4"
src/main.rs（官方教學）
use mini_redis::{client, Result};

#[tokio::main]
async fn main() -> Result<()> {
    // Open a connection to the mini-redis address.
    let mut client = client::connect("127.0.0.1:6379").await?;

    // Set the key "hello" with value "world"
    client.set("hello", "world".into()).await?;

    // Get key "hello"
    let result = client.get("hello").await?;

    println!("got value from the server; result={:?}", result);

    Ok(())
}

先在另一個終端機執行 mini-redis-server（未安裝時可用 cargo install mini-redis），再執行 cargo run，官方給出的輸出為：

執行結果（官方教學）
$ cargo run
got value from the server; result=Some(b"world")

官方特別指出：雖然操作是非同步的，程式碼看起來像同步，唯一的線索是 .await。

Rust 的 async 是惰性的

Tokio 教學強調，呼叫 async fn 不會執行函式本體，而是回傳一個代表該操作的值，概念上類似零參數閉包；要真正執行必須對回傳值 .await。下例會先印出 hello，再印出 world：

Tokio 教學：惰性執行
async fn say_world() {
    println!("world");
}

#[tokio::main]
async fn main() {
    // Calling `say_world()` does not execute the body of `say_world()`.
    let op = say_world();

    // This println! comes first
    println!("hello");

    // Calling `.await` on `op` starts executing `say_world`.
    op.await;
}

#[tokio::main] 做了什麼

async 函式必須由 runtime 執行。runtime 包含非同步 task 排程器、事件驅動 I/O 與計時器等，而且不會自動啟動，所以 main 要負責啟動。#[tokio::main] 是個巨集，把 async fn main() 轉成同步的 fn main()，內部初始化 runtime 並執行原本的 async main。官方給的轉換前後如下：

轉換前（官方教學）
#[tokio::main]
async fn main() {
    println!("hello");
}
轉換後（官方教學）
fn main() {
    let mut rt = tokio::runtime::Runtime::new().unwrap();
    rt.block_on(async {
        println!("hello");
    })
}
ℹ️
Cargo features

教學使用 features = ["full"]。Tokio 功能很多（TCP、UDP、Unix socket、計時器、同步工具、多種排程器等），要壓低編譯時間或最終體積時，可只啟用用到的 feature。axum 文件也提醒：使用 #[tokio::main] 需要啟用 tokio 的 macros 與 rt-multi-thread feature，或直接用 full。

Task、計時器與逾時

以下範例取自 Medium 作者 Aarambh Dev Hub 的教學（2024-09，個人部落格，非官方）。tokio::spawn 建立在背景獨立執行的 task；用 .await 等待它們結束。文章給出的輸出顯示 task two（睡 1 秒）比 task one（睡 2 秒）先完成。

spawn 兩個 task（依該文章）
use tokio::time::{sleep, Duration};

#[tokio::main]
async fn main() {
    println!("Hello, Tokio!");

    let task_one = tokio::spawn(async {
        println!("Task one is started");
        sleep(Duration::from_secs(2)).await;
        println!("Task one is done");
    });

    let task_two = tokio::spawn(async {
        println!("Task two is started");
        sleep(Duration::from_secs(1)).await;
        println!("Task two is done");
    });

    // Await the tasks to complete
    task_one.await.unwrap();
    task_two.await.unwrap();
}

tokio::time::timeout 可為操作設時限；下例中的任務需 2 秒、時限 1 秒，所以會得到逾時結果。

逾時（依該文章，補上原文片段省略的 sleep 匯入）
use tokio::time::{sleep, timeout, Duration};

#[tokio::main]
async fn main() {
    let result = timeout(Duration::from_secs(1), async {
        sleep(Duration::from_secs(2)).await;
    }).await;

    match result {
        Ok(_) => println!("Task completed successfully"),
        Err(_) => println!("Task timed out"),
    }
}

上一章已提過的陷阱在此同樣適用：不要在 async 中呼叫阻塞操作，需要時改用 spawn_blocking。

axum：路由、handler、extractor

axum 的定位（docs.rs/axum）是專注於易用與模組化的 HTTP 路由與請求處理函式庫，特色包括：不靠巨集的路由 API、以 extractor 宣告式解析請求、簡單可預期的錯誤處理模型、極少樣板的回應產生，以及完整利用 tower 與 tower-http 的中介軟體生態。官方說這最後一點是 axum 與其他框架最大的差別：axum 沒有自己的中介軟體系統，而是用 tower::Service，因此免費取得逾時、追蹤、壓縮、授權等功能，也能與 hyper、tonic 寫的應用共用中介軟體。相容性方面，axum 是為 tokio 與 hyper 設計的，官方明說目前不以 runtime 與傳輸層獨立為目標。

axum 的 Hello, World（官方文件）
use axum::{
    routing::get,
    Router,
};

#[tokio::main]
async fn main() {
    // build our application with a single route
    let app = Router::new().route("/", get(|| async { "Hello, World!" }));

    // run our app with hyper, listening globally on port 3000
    let listener = tokio::net::TcpListener::bind("0.0.0.0:3000").await.unwrap();
    axum::serve(listener, app).await.unwrap();
}

Router 設定路徑對應到哪個服務：

路由（官方文件）
use axum::{Router, routing::get};

// our router
let app = Router::new()
    .route("/", get(root))
    .route("/foo", get(get_foo).post(post_foo))
    .route("/foo/bar", get(foo_bar));

// which calls one of these handlers
async fn root() {}
async fn get_foo() {}
async fn post_foo() {}
async fn foo_bar() {}

在 axum 中，handler 是接收零個或多個 extractor、並回傳可轉成回應之物的 async 函式；應用邏輯就寫在 handler 裡。extractor 是實作 FromRequest 或 FromRequestParts 的型別，用來拆解請求：

Extractor（官方文件）
use axum::extract::{Path, Query, Json};
use std::collections::HashMap;

// `Path` gives you the path parameters and deserializes them.
async fn path(Path(user_id): Path<u32>) {}

// `Query` gives you the query parameters and deserializes them.
async fn query(Query(params): Query<HashMap<String, String>>) {}

// Buffer the request body and deserialize it as JSON into a
// `serde_json::Value`. `Json` supports any type that implements
// `serde::Deserialize`.
async fn json(Json(payload): Json<serde_json::Value>) {}

任何實作 IntoResponse 的型別都能從 handler 回傳：

回應（官方文件）
use axum::{
    body::Body,
    routing::get,
    response::Json,
    Router,
};
use serde_json::{Value, json};

// `&'static str` becomes a `200 OK` with `content-type: text/plain; charset=utf-8`
async fn plain_text() -> &'static str {
    "foo"
}

// `Json` gives a content-type of `application/json` and works with any type
// that implements `serde::Serialize`
async fn json() -> Json<Value> {
    Json(json!({ "data": 42 }))
}

let app = Router::new()
    .route("/plain_text", get(plain_text))
    .route("/json", get(json));

Serde：JSON 的基礎

Json extractor 與回應之所以能用，是因為資料型別實作了 Serde 的 Serialize／Deserialize。Serde 官方網站說明：許多語言靠執行期反射做序列化，Serde 則建立在 Rust 的 trait 系統上，可用 derive 屬性在編譯期自動產生實作，沒有反射或執行期型別資訊的負擔，在許多情況下能與手寫序列化器一樣快。

Serde 官方首頁範例
use serde::{Serialize, Deserialize};

#[derive(Serialize, Deserialize, Debug)]
struct Point {
    x: i32,
    y: i32,
}

fn main() {
    let point = Point { x: 1, y: 2 };

    // Convert the Point to a JSON string.
    let serialized = serde_json::to_string(&point).unwrap();

    // Prints serialized = {"x":1,"y":2}
    println!("serialized = {}", serialized);

    // Convert the JSON string back to a Point.
    let deserialized: Point = serde_json::from_str(&serialized).unwrap();

    // Prints deserialized = Point { x: 1, y: 2 }
    println!("deserialized = {:?}", deserialized);
}

狀態共享

axum 文件列出四種常見的 handler 狀態共享方式：State extractor、request extension、閉包捕獲、task-local 變數。官方建議盡可能用 State，因為型別較安全，缺點是比 task-local 與 extension 更不具動態性。

State extractor（官方文件）
use axum::{
    extract::State,
    routing::get,
    Router,
};
use std::sync::Arc;

struct AppState {
    // ...
}

let shared_state = Arc::new(AppState { /* ... */ });

let app = Router::new()
    .route("/", get(handler))
    .with_state(shared_state);

async fn handler(
    State(state): State<Arc<AppState>>,
) {
    // ...
}
  • State 會為每個請求複製（clone）；用 Arc 包起來可讓複製很便宜。若所有欄位本來就便宜複製，可直接在 struct 上 #[derive(Clone)]。
  • 只需要部分狀態時，可用 FromRef 取出子狀態。
  • Router<S> 的 S 若不是 ()，表示這個 router 還「缺少」一個型別 S 的狀態；呼叫 .with_state(s) 補上後通常得到 Router<()>，這才是能傳給 serve() 的形態。
  • request extension 的缺點：extractor 找不到對應的 extension（例如忘了加 layer、型別取錯）時，是執行期錯誤，回應 500 Internal Server Error。閉包捕獲則是最囉嗦的做法。
⚠️
版本差異：路徑參數語法

Reintech 2026 文章的範例用 "/users/:id"，而 docs.rs 最新版 axum 文件的閉包捕獲範例用 "/users/{id}"。兩者不同，素材未說明版本變更的原因，實作時請以你採用的 axum 版本文件為準。

素材未涵蓋的部分

簡介中提到的優雅關閉、觀測性（tracing 與 metrics）與效能調校，本章素材都沒有講解，故未展開；axum 的錯誤處理與中介軟體，素材也只指向文件的 error_handling 與 middleware 模組，沒有範例。若要實作請直接參閱 docs.rs 與 tokio.rs。
